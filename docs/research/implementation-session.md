# 実装セッションの設定（2026-10-08）

卒業研究「Minecraft（MineColonies MOD）を用いたゲーム社会シミュレーション」のうち、**建物の配置まわりの実装を担当するセッション**の設定です。新しいセッションでこの文書を読み込めば、同じ役割で作業を始められます。範囲はユーザーと相談して調整する。

## セッションの分担

| セッション | 担当 | 文書 |
| --- | --- | --- |
| 方針セッション | 研究の方向・評価の考え方・ルールを決める | `docs/research/research-direction-notes.md` |
| 仕様把握セッション | MineColonies で何ができるかを根拠つきで確認する | `docs/sessions/minecolonies-spec-session.md`、`docs/research/minecolonies-spec-notes.md` |
| 論文読み込みセッション | 論文を読み、ノートを作る | `docs/sessions/paper-reading-session.md`、`docs/reference/paper-notes/` |
| **実装セッション（この文書）** | 方針と仕様に基づいてコードを書き、動作を確かめる | `docs/research/implementation-log.md`（作業記録。初回に作る） |

## 担当する範囲

- VoyagerBridge（`YacobiHime/minecolon_sim` の Forge MOD）の配置処理の見直し
  - 判定を「ハード制約 → 評価関数（差し替え可能）→ 設置（判定なし）」の3段にまとめる。代替を使ったときは、緩めた制約を記録する。
  - 入口の表: 設計図の中で「外から小屋ブロックまで歩いて行けるか」を塗りつぶしで調べ、建物の種類ごとに入口の面と位置を求める。
  - 回転: 候補を「場所 × 4方向」にする。
- 取り壊し・移転の窓口（解体＋回収、移転と市民の割り当て直し）。ルールは方針メモの1章。
- **配置を見て直すツール**（下の節）。
- 代理モデル（軽い2Dグリッド、Python）。マイクラ側と**同じルール**で実装する。
- テスト用のマップと、自動チェック（重なり、範囲全体が領土内、入口から出られる、など）。

## 担当しない範囲（ほかのセッションへ回す）

- 研究の方向・評価指標の選び方・ルールの変更 → 方針セッション。「方針セッションへの申し送り」として作業記録に書く。
- MineColonies の仕様が分からない点 → 仕様把握セッション。推測で実装を進めない。
- LLM 市長（`council.js`）や社会モデル（`social_*.js`）など、配置以外の部分。同期の担当範囲と重なる可能性があるので、触る前にユーザーに確認する。

## 動かす場所（2026-10-08 決定）

- コードは GitHub のリポジトリにあるので、**書くのはどのパソコンでもよい**。
- **Minecraft サーバーで動作を確かめるのは研究室のデスクトップ PC**。前期と同じく、ノートPCから Tailscale で研究室のデスクトップに接続し、Claude Code で開発する。
- サーバーが要らない作業（設計図からの入口の表の生成、代理モデル、単体テスト、コードレビュー）は、どこで進めてもよい。
- リポジトリに `CLAUDE.md` を置き、ビルド・起動・テストの手順と、このセッションのルールを書いておく。どのパソコン・どのセッションでも同じ前提で始められ、後輩への引き継ぎ資料にもなる。

## 作業のルール

- 根拠: 方針メモ（`docs/research/research-direction-notes.md`）と仕様ノート（`docs/research/minecolonies-spec-notes.md`）に従う。食い違いや不足があれば、実装の前にユーザーに伝える。
- 進め方: 変更ごとにブランチを切る。大きな変更は、先に計画だけを示してユーザーの了承を得る（Claude Code の plan mode）。既存の挙動を変えるときは、変更前後の違いをテスト用のマップで示す。
- 記録: 設計の判断、確かめた結果、未解決の問題を `docs/research/implementation-log.md` に追記する。

## レビューの仕組み（2026-10-08 決定。重要）

**配置もコードもサブエージェントも、最終的な判断はユーザーがレビューして決める。** AI は作業を「判断しやすい形」にまとめて渡し、ユーザーは判定と理由を1行残す。残った理由は、レビュー役エージェントのメモリと、配置の評価関数の材料として使う。

| 対象 | AI が用意するもの | ユーザーがすること | 記録先 |
| --- | --- | --- | --- |
| 配置 | 配置を見て直すツールに AI の配置案を表示する | 承認／動かす／却下を選び、理由を1行書く | 修正の記録（JSON） |
| コードの変更 | GitHub のプルリクエスト（PR）。中身はテンプレートで固定する | PR 上で承認か差し戻し。差し戻すときは理由を書く | PR のコメント |
| サブエージェント | PR のテンプレートの「使ったサブエージェント」欄 | 各エージェントに「役に立った／不要」を付ける | 作業記録の「サブエージェントの使用記録」 |

### PR のテンプレート（`.github/pull_request_template.md` に置く）

1. 何を変えたか（3行以内）
2. ハード制約の自動チェック結果（重なり・範囲全体の領土・水・平らさ・ビルダーの範囲・入口の合否）
3. 変更前後の配置図（テスト用マップ）
4. 使ったサブエージェントと、それぞれが見つけたこと（何も見つけなかった場合もそう書く）
5. ユーザーに判断してほしい点

### 運用

- コードの変更は、小さくても PR を通す。main への直接の push はしない。
- サブエージェントが動いた記録（名前・時刻）は、フック（`SubagentStop`）で自動的に作業記録へ残す。ユーザーが書くのは「役に立ったか」だけにする。
- 差し戻しの理由は、レビュー役エージェント（`placement-reviewer`）のメモリに反映させる。同じ指摘を二度させない。
- PR は GitHub のスマホアプリからも見られるので、研究室の外でもレビューできる。

## モデル選びの方針（2026-10-08）

- **コードを書く作業には強いモデルを使う。** 前期、コーディングを弱めのモデルに任せたところ、トークン消費はあまり変わらず、効果が低かった（ユーザーの経験）。手直しが増えると、結局高くつく。
- 安いモデルを使うのは、判断の要らない作業に限る（テストやビルドのログの要約、ファイルの検索など）。
- レビュー役には強いモデルを使う。

## Claude Code の機能の使い方（2026-10-08、公式ドキュメント https://code.claude.com/docs/ja/sub-agents を確認）

### 運用の方針（ユーザーの判断、2026-10-08）

- サブエージェントは**まず色々と試し、ユーザーが効果的だと判断したものだけ続け、不要なものは切り捨てる**。トークン消費との兼ね合いがあるので、使えば使うほど良いとは考えない。
- 判断の材料として、サブエージェントを使ったら作業記録（`docs/research/implementation-log.md`）の「サブエージェントの使用記録」に1行ずつ残す: 日付／エージェント名／何をさせたか／役に立ったか（見つけた問題など）／重さ（体感、または `/cost` などで見た消費）。
- 「エージェントチーム」「セッション間のメッセージ」は、必要になってから検討する（今は使わない）。

### カスタムサブエージェントの構成（試す候補）

リポジトリの `.claude/agents/` に Markdown（先頭に frontmatter）で定義する。`.claude/agents/` はリポジトリに含めるので、同期・後輩とも共有できる。

| 名前（案） | 役割 | 主な設定 |
| --- | --- | --- |
| `placement-reviewer` | 変更のレビュー。観点は下の一覧 | `tools: Read, Grep, Glob, Bash`（Bash は `git diff` などの確認用）。書き換えはしない。`memory: project`（繰り返し出る問題を覚えさせる）。`model: opus` |
| `test-runner` | ビルドとテスト用マップでの自動チェックを回し、失敗だけを要約して返す | `model: sonnet` など安いモデル。ログの山をメインの会話に持ち込まない |
| `spec-lookup` | 実装中に出た MineColonies の細かい疑問を、仕様ノートとソースで調べる。確定できなければ「仕様把握セッションへ」と返す | 読み取り専用。`memory: project` |
| 組み込みの `Explore` | 既存コードの調査（例: VoyagerBridge の52個の窓口の一覧と依存関係の地図） | 定義不要。読み取り専用で、結論だけ返す |

レビューの観点（`placement-reviewer` の本文に書く）:

- ハード制約の抜け（重なり、範囲全体の領土、水、平らさ、ビルダーの範囲、入口）
- 既存の挙動が意図せず変わっていないか
- 判定が「ハード制約 → 評価関数 → 設置」の3段の外に漏れていないか（つぎはぎを増やさない）
- 代理モデルとマイクラ側でルールが食い違っていないか
- 担当外のファイル（`council.js`、`social_*.js` など）に触れていないか

### 使える機能と使いどころ

| 機能 | 内容 | この研究での使いどころ |
| --- | --- | --- |
| `memory`（永続メモリ） | サブエージェントが会話をまたいで学んだことを `.claude/agent-memory/<名前>/` に残す。`project` ならリポジトリで共有できる | レビュー役に「この repo でよく起きる問題」（self-heal のような遠回しな修正、ハード制約の抜け）を覚えさせ、回を重ねるほど鋭くする |
| `skills`（スキルの先読み） | 起動時にスキルの中身をサブエージェントに読み込ませる | 「配置のルール（ハード制約の一覧と3段の構成）」をスキルにして、実装役・レビュー役の両方に読ませる。ルールの書き場所を1か所にできる |
| `hooks`（フック） | ツールを使う前後にスクリプトを自動で走らせる。終了コード2で操作を止められる | 編集のたびに Java のコンパイル（`PostToolUse`）を走らせ、エラーをすぐ返す。担当外のファイル（`council.js` など）の編集を止める（`PreToolUse`） |
| `isolation: worktree` | サブエージェントを別の作業コピー（git worktree）で動かす | 入口の表・代理モデル・配置処理の整理を並行で進めても、互いのファイルを壊さない |
| `tools` / `disallowedTools` | 使える道具を制限する | レビュー役には書き換えをさせない |
| `model` | サブエージェントごとにモデルを選ぶ | 判断が要るレビューは強いモデル、ログの要約や調査は安いモデルで費用を抑える |
| バックグラウンド実行 | サブエージェントがメインの会話と並行して動く | ビルドやテストを走らせている間に、ほかの作業を進める |
| `--agent` / `agent` 設定 | セッション全体をそのエージェントとして起動する | 「実装セッションの進行役」を定義しておけば、毎回この文書を読ませなくても同じ役割で始められる |
| `@` で指名 | `@"placement-reviewer (agent)"` のように指名すると、確実にそのエージェントが動く | レビューの呼び忘れを防ぐ |

- 注意: サブエージェントの説明（`description`）は常にコンテキストを使うので短く書き、詳しい指示は本文に書く。

## 配置を見て直すツール（案）

方針メモ4章（人間の配置のニュアンスを取り入れる）の「修正を記録する」形を実現するための道具。

- 表示: `/status` などから建物の位置・範囲・回転・入口を取り、2Dの地図（上から見た図）に描く。高さマップ（`/heightmap`）と水も重ねる。
- 操作: 建物をドラッグで動かす、回転させる。動かしたときに「なぜ動かしたか」を1行入力する。
- 記録: 「AIの配置 → 人の修正 → 理由」を1件ずつファイル（JSON など）に保存する。これが評価関数の項や重みを作る材料になる。
- 反映（後の段階）: 修正をそのまま移転の窓口でゲームに反映する。最初は記録だけでよい。
- 置き場所: VoyagerBridge は研究室のデスクトップの中で動いているので、ツールもそこ（またはTailscale でつながる範囲）で動くローカルのWebページにする。claude.ai で公開するページからは、研究室のPCに直接つなげない。
- 代理モデルと同じ地図の表現を使えば、代理モデルの結果を見る画面としても使える。

## 現状の把握（出発点）

- 配置は VoyagerBridge の `findPlacementPos` がルールで決めている。制約の一覧は `docs/research/minecolonies-esa-article.md` の11.4節と方針メモの3章。
- 判定が `findPlacementPos`・`placeOnServerThread`・`/requestBuild` の3か所に分散。範囲全体の領土は `/requestBuild` 直前の強制確保（self-heal）で補っている。
- 回転は0に固定。入口の情報はない（設計図のドアからの推定では48種類中31種類で入口の面が分かった。多くは南向き）。
- レベルによる範囲の変化はほぼない（Colonial 48種類中47種類で同じ）。

## 当面の作業: 前提を確かめる実験 A〜D（2026-10-14、方針セッションから依頼）

計画の本体は `docs/research/experiment-plan.md`。目的・手順・記録する項目・判断の基準はそちらに従う。実装セッションの役割は、**ユーザーと一緒に実験を順番に進め、記録と判断の材料をそろえること**。研究の方向に関わる判断（判断の基準の表の結論）はユーザーが行い、方針セッションに持っていく。

### 進める順番

1. **準備**: 実験用ワールドの用意（本番のコピー＋バックアップ）と、観測用スクリプトの作成（下）
2. **実験 A**（領土を広げる）
3. **実験 B**（自分の町を変換する）。A の結果で範囲を決める
4. **実験 C**（市民は川を渡るか）、**実験 D**（仮設の小屋 ①）。順番は自由

1つ終わるごとに、`docs/research/experiment-log.md` に記録し、ユーザーに結果と「判断の基準」に照らした見立てを示して、次へ進むか確認する。

### 準備で作るもの: 観測用スクリプト

- VoyagerBridge の `/status` などを一定の間隔で呼び、市民の位置・仕事の状態・建物の建設の進み具合・時刻（ゲーム内と現実）を CSV か JSON に記録するスクリプト。
- 実験 A（離れた地区が動いているか）、C（市民の通り道）、D（建設の時間）で共通に使う。
- 記録は実験ごとのファイルに分け、`experiment-log.md` からファイル名で参照する。
- TPS も一緒に記録できると良い（取り方は【要確認】）。

### 実験ごとのサブエージェントの使い方（試す候補。使ったら作業記録の「サブエージェントの使用記録」に1行残す）

| 実験 | サブエージェント | させること |
| --- | --- | --- |
| 準備 | 組み込みの `Explore` | VoyagerBridge の窓口のうち、観測に使えるもの（`/status` など）と、領土・チャンクの読み込みに関わるもの（`forceLoadAndClaim` など）を洗い出す |
| 準備 | `placement-reviewer` | 観測用スクリプトのレビュー（ゲームの状態を書き換えていないか、記録の抜けがないか） |
| A | `spec-lookup` | `/mc colony claim` の正確な書き方、サーバー設定ファイルの名前、TPS の見方を調べる。研究室の版（1.1.1231）で確認する |
| A | バックグラウンド実行のエージェント（安いモデル） | 観測の記録を見張り、「止まった市民・止まった建設」が出たら要約して知らせる |
| B | 汎用のエージェント | Arnis の出力する Minecraft のバージョンと設定を調べ、1.20.1 で使う方法を探す（ウェブ調査） |
| C・D | `test-runner` 相当（安いモデル） | 観測の記録（CSV/JSON）を集計し、渡り方・建設時間などの表にして返す |
| 全体 | `placement-reviewer` | 実験のために VoyagerBridge に手を入れた場合は、必ずレビューする |

- 方針（ユーザーの判断）: サブエージェントは試して、効果的なものだけ続ける。トークン消費とのバランスを見る。コードを書く作業とレビューには強いモデルを使う。
