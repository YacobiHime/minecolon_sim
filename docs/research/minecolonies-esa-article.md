# 1. MineColonies の概要

## 1.1 どんな MOD か

- LDTTeam（Let's Dev Together Team）が開発している、Minecraft 用の町づくり MOD。ソースコードは GitHub で GPL-3.0 として公開されている。
- プレイヤーは**市長（mayor）**としてコロニー（町）を作る。NPC の**市民（citizen）**が、建築・農業・漁業・採掘・製造・輸送・防衛などの仕事を自分で判断して進める。
- 建物は**スケマティック（設計図）**として用意されている。プレイヤーが場所を決めると、**ビルダー**が必要な資材を要求しながら自動で建てる。
- ほとんどの建物は**レベル1〜5**に改築でき、レベルが上がるほど雇える人数・扱えるレシピ数・効果範囲などが増える（一部の建物は最大レベル3）。
- 市民は**スキル・幸福度・満腹度・住居・職場・病気**などの状態を持つ。出生・病気・死亡・喪など、社会的な出来事も起こる。

## 1.2 対応バージョン（2026年9月時点）

| Minecraft | MOD ローダー | MOD 本体のブランチ | 備考 |
| --- | --- | --- | --- |
| 1.20.1 | Forge | `version/main` | 2026-09 時点でも更新が続いている |
| 1.21.1 | NeoForge | `version/1.21` | CurseForge で `minecolonies-1.1.xxxx-1.21.1.jar` として配布されている |

- 公式 Wiki は 1.18〜1.21.1 を対象にしていて、ページ内にバージョンごとの記述の違いがある。
- 1.20 以降は一部の建物名・職業名が変わっている（例: Restaurant → Dining Hall、Cook → Waiter、Stone Smeltery → Brick Yard）。この記事では 1.20 以降の名前を使う。
- 研究室の実装は **Minecraft 1.20.1（Forge）＋ MineColonies 1.20.1-1.1.1231** で動いている（→ 10.1）。

## 1.3 前提 MOD

| MOD | 役割 |
| --- | --- |
| Structurize | スケマティック（設計図）の建築処理。ビルドツール・スキャンツール・シェイプツールなどを提供する |
| Domum Ornamentum | 装飾ブロックを組み合わせてクラフトする仕組み |
| BlockUI | XML ベースの GUI ライブラリ |
| Multi-Piston | 複数のブロックをまとめて動かせるピストン |

## 1.4 コロニー開始の流れ（公式「Getting Started」の要約）

1. **コロニーを作る**: 補給キャンプ（Supply Camp）／補給船（Supply Ship）を置く（1ワールドにつき1回）と、町役場ブロック・ビルドツール・初期資材が手に入る。ワールド生成で出てくる**放棄されたコロニー**を作り直す方法もある。
2. **町役場（Town Hall）を置いて創設する**。初期市民は4人（設定で変更可）。町役場の位置を中心に、初期設定では半径4チャンクが領土になる。**この中心は後から変えられない**。
3. **ビルダーの小屋（Builder's Hut）**を最初に建てる。
4. **住居**（酒場・住宅）と**食料**（漁師・農家・食堂）を用意する。
5. **木こり**と**鉱山**で木材・石材・鉱石を確保する。
6. **倉庫**と**配達員の小屋**で物流を自動化する。
7. 衛兵塔（襲撃への備え）、大学（研究）、病院などを増やしていく。

## 1.5 時間の進み方

- 市民は日中に働き、夜は家に帰って寝る。Minecraft の1日は現実の20分。
- 公式 Wiki では「雨・雪・夜のあいだと、前日に市民が死亡した日は仕事を休む」とされている。
  - 【ソース確認】実際には、衛兵は雨でも働く。喪で休むのは亡くなった市民の家族・同居人だけ（翌日）。研究 Rainman を完了するか、設定 `workersalwaysworkinrain` を有効にすると雨でも働く。
- 研究「Night Owl」「Night Owl II」で、1日の労働時間が +1時間／+2時間になる【ソース確認】。
- 研究の進み具合は、ゲーム内の時間ではなく**現実の時間**で進む。

# 2. MineColonies の構成（プログラム的な全体像）

> **この章は作成中です。** ソースコードを読んで、クラス構成・データの流れ・API の入口を追記する予定です。いまは、これまでの調査で読んだファイルの場所だけを載せています。

## 2.1 リポジトリの大まかな構成【ソース確認】

ソースコードは `src/main/java/com/minecolonies/` の下に、大きく次の3つに分かれています。

| パッケージ | 役割（これまでに読んだ範囲での理解） |
| --- | --- |
| `api` | ほかの MOD から使うためのインターフェースや定数（設定、統計の項目名など） |
| `apiimp` | `api` の実装の登録処理（幸福度の要因の登録など） |
| `core` | 本体の実装（コロニー、市民、建物、イベント、コマンドなど） |

データパックで変えられるデータ（研究・病気・クエストなど）は JSON として `src/datagen/generated/minecolonies/data/minecolonies/` に生成されています。

## 2.2 これまでに読んだファイル【ソース確認】

| 統計の項目名 | `api/util/constant/StatisticsConstants.java` |

| 病気の発症・感染 | `core/entity/citizen/citizenhandlers/CitizenDiseaseHandler.java` |

| 出生 | `ReproductionManager.java` |

| 研究の定義 | `core/generation/defaults/DefaultResearchProvider.java` |
| コマンド | `core/commands/EntryPoint.java` |

## 2.3 研究の実装が使っている MineColonies の API【実験で確認】

研究室の VoyagerBridge（11章、付録C）は、MineColonies の次のクラス・メソッドを外から呼んで動いています。MineColonies を外から操作するときの、実績のある入口です。

| やりたいこと | 使っている API |
| --- | --- |
| コロニーの創設 | `IColonyManager.createColony(...)` |
| 建物の設置と登録 | ハットブロックを `setBlockAndUpdate` で置き、`setPlacedBy(...)` で建物として登録させる。スタイル（Colonial）と設計図のパスを設定する |
| 建築・改築の依頼 | `building.requestUpgrade(player, builderHutPos)`（通常のワークオーダーができる） |
| ワークオーダーの付け替え | `setClaimedBy` と、元のビルダーの `onWorkOrderCancellation()` |
| 雇用・配属 | `WorkerBuildingModule.assignCitizen` / `removeCitizen`、`setHiringMode` |
| 住居の割り当て | `LivingBuildingModule.assignCitizen` / `removeCitizen` |
| 研究の開始 | `IGlobalResearch.startResearch(...)` |
| 食堂のメニュー | `RestaurantMenuModule.addMenuItem` |
| レシピの教示 | `RecipeStorage` を作って `addRecipe` |
| 要求の強制解決 | `building.overruleNextOpenRequestOfCitizenWithStack(...)` |
| 市民の追加 | `spawnOrCreateCivilian` |
| 幸福度・スキルの読み出し | `getCitizenHappinessHandler().getHappiness(...)`、`getCitizenSkillHandler().getLevel(...)` |

# 3. MineColonies で実現されている要素（大枠）

ここでは「どんな要素があるか」を大まかに説明します。数値や計算式は 4章、データの取り方は 5章で扱います。

| 要素 | 概要 | 詳細 |
| --- | --- | --- |
| 市民 | スキル（11種類）・幸福度・満腹度・住居・職場・健康を持つ NPC。大人は職業に就き、子どもは学校に通って成長する。家族関係（パートナー・親子・兄弟姉妹）も持つ | 4.1〜4.6 |
| 職業 | 45種類。採取・畜産・製造・衛兵・その他に分かれ、職業ごとに主スキル・副スキルがある | 3.1 |
| 建物 | 51種類。ハットブロックを中心に建ち、多くはレベル1〜5に改築できる。多くの建物は研究で解放される | 3.2 |
| 物流（リクエストシステム） | 通貨はなく、市民が必要な物を「要求」し、倉庫から配達員が届けるか、作れる職人が作る。誰にも解決できない要求はプレイヤーに回ってくる | 3.3 |
| 食料 | 農家・畜産・漁師 → 料理人 → 給仕（食堂）の生産チェーン。独自作物はバイオームで育つ場所が決まる | 4.4 |
| 住居と人口 | 空きベッドがあると新しい市民が来る。出生、酒場の訪問者の勧誘でも増える | 4.2、4.3 |
| 教育 | 学校（子ども）と図書館（大人）で Intelligence を上げる | 4.1 |
| 研究 | 大学で研究者が研究を進め、建物の解放・能力の向上・人口上限の引き上げなどが起こる。市民・戦闘・技術の3ツリー | 3.4 |
| 病気と医療 | 自然発症と接触感染があり、病院で医師が治療する | 4.5 |
| 死亡と喪 | 市民が死ぬと家族・同居人が喪に服し、幸福度が下がる。墓地で蘇生を試みられる | 4.6 |
| 襲撃（特殊イベント） | 夜の始まりに、バイオームに応じた襲撃者（蛮族・海賊など）がやってくる。難易度は結果に応じて自動で変わる | 4.7 |
| 防衛 | 衛兵（騎士・弓兵・ドルイド・騎兵）が巡回・警備する | 3.5 |
| 領土と保護 | コロニーはチャンク単位の領土を持ち、建物を建てると広がる。領土内は爆発やほかのプレイヤーの破壊から守られる | 4.8 |
| 外交 | ゲートハウスどうしを看板の道でつなぐ「コロニー接続」と、同盟・敵対の宣言がある。コロニー間の取引機能は確認できていない【要検証】 | 3.5 |
| クエスト | 市民がプレイヤーに依頼を持ってくる。データパックで独自に作れる | 3.6 |

## 3.3 物流（リクエストシステム）

MineColonies には**お金も市場もありません**。コロニー内の経済は次の流れで回ります。

```
市民が作業に必要なアイテムに気づく
  → 自分の持ち物・職場にあれば作業を続ける
  → なければ自動でリクエストを出す
      → 倉庫にある → 配達員が届ける
      → 倉庫にない → 作り方を知っている職人がいれば、職人が材料をリクエストして作る（連鎖する）
      → 誰も作れない → プレイヤーの対応待ち（市民の頭上に赤い歯車が出る）
```

- いろいろな職業の市民がいるほど、多くのリクエストが自動で解決する。
- 建物ごとに、配達員が物を回収しに行く優先度（1〜10）や、常に手元に置いておく**最低在庫**を設定できる。
- 物流の規模は、倉庫と配達員の小屋のレベル、配達員の人数とスキル、道の整備で決まる。

## 3.4 研究

- **大学**で**研究者**が研究を進める。ツリーは **市民・戦闘・技術** の3つ。
- ツリーの列（1〜6）が、その研究に必要な大学のレベルを表す。**列6の研究は、各ツリーで1つしか完了した状態にできない**。
- 「or」で結ばれた研究は同時に1つしか選べない（**排他**）。例: 教育速度を上げる More Books 系か、子どもの成長を速める Nurture 系か。
- 研究を始めるには、材料を**プレイヤーの持ち物**に入れておく必要がある。
- 研究ツリーはデータパックで変更・追加・削除できる。
- 【実験で確認】研究は全部で4ブランチ・206件（非表示のツリーを含む）。研究室のコロニーでは、自動投入で無人運転のあいだに141件を完了した。

## 3.5 防衛と外交

- **衛兵**: 騎士（近接）・弓兵（遠距離）・ドルイド（ポーションで支援）・騎兵（軍馬）。研究で斧の Huscarl、クロスボウの Marksman も解放される【ソース確認】。任務は巡回・警備・プレイヤー追従から選ぶ。
- **襲撃**: 夜の始まりに発生し、市民は仕事をやめて家に逃げる。襲撃者の種類は出現場所のバイオームで決まる（タイガ: ノルド人、砂漠: ミイラ、大きな水域: 海賊、ジャングル: アマゾン、その他: 蛮族）。襲撃者はドアやブロックを壊し、はしごや橋を架けながらハットブロックを目指す。
- **権限**: 町役場で、ほかのプレイヤーに Owner・Officer・Friend・Neutral・Hostile のランクを与えられる【ソース確認】。
- **コロニー接続**: 両方のコロニーにゲートハウスを建て、50ブロック以内ごとに看板を置いて、市民が歩ける道でつなぐ。公式 Wiki では「将来の取引・外交機能の基盤」と説明されている。
- **同盟・敵対**: 接続したコロニーどうしが**同じ関係を設定したときだけ**有効になる。同盟コロニーにはテレポートできる。敵対は初期設定では特に効果がない。

## 3.6 クエストと訪問者

- **クエスト**: 市民がプレイヤーに依頼を持ってくる。目標は会話・納品・建築・ブロックの破壊/設置・討伐・研究の完了。
  - 【ソース確認】データパック `colony/quests` に JSON で定義されている。報酬はアイテムのほかに、幸福度・評判・襲撃の調整・市民どうしの関係（パートナー）・研究・スキル・別クエストの解放がある。
  - 独自のクエストを作れば、「イベント」や「選択を迫られる出来事」をシナリオとして組み込める可能性がある【要検証】。
- **酒場の訪問者**: 要求されたアイテムを渡すと、コロニーの市民として勧誘できる。勧誘に必要なアイテムはデータパック `colony/recruitment_items` で定義されている【ソース確認】。

# 4. MineColonies の仕様（数値が絡むパラメータ）

## 4.1 スキル

- **11種類**: Athletics、Dexterity、Strength、Agility、Stamina、Mana、Adaptability、Focus、Creativity、Knowledge、Intelligence。
- 市民は働くことでスキルが上がる。上がる速さは**職場のレベル**と **Intelligence** で決まる。
- スキルの上限は**住居のレベル**で決まる。【ソース確認】上限は `(住居レベル + 1) × 10` で、最大レベルが5の住居をレベル5まで上げたときだけ 99 になる（`CitizenSkillHandler.java`）。

| 住居 | スキル上限 |
| --- | --- |
| 住居なし | 10 |
| 住宅 レベル1 | 20 |
| 住宅 レベル2 | 30 |
| 住宅 レベル3 | 40 |
| 住宅 レベル4 | 50 |
| 住宅 レベル5 | 99 |
| 酒場（最大レベル3） | レベル1〜3で 20 / 30 / 40。最大レベルが5未満の建物なので、99 にはならない |

- 学校の生徒数・図書館の学生数は、それぞれ建物レベル×2（レベル5で10人）。

## 4.2 人口と出生

- **初期市民**: 4人（設定 `initialcitizenamount`、1〜10）。
- **人口の上限** = min(ベッド数, 研究による上限, 設定の上限)【ソース確認】
  - 研究なしの上限は **25人**。研究 Outpost → Hamlet → Village → City で 50 → 100 → 150 → 500。
  - 設定 `maxcitizenpercolony` の初期値は **250**（25〜500）。
- **増え方**: ①空きベッドがあると新しい市民が来る、②出生、③酒場の訪問者の勧誘。
- **出生の条件**【ソース確認】（`ReproductionManager.java`）: 数分〜十数分ごとに判定され、条件は次の4つだけ。お金や資源は関係しない。
  1. コロニーに男性と女性が少なくとも1人ずついる
  2. 空きベッドのある家がある
  3. 人口が上限未満
  4. 町役場の設定で新しい市民の出現がオンになっている
- 子どもの親は、**生まれた建物に住んでいる大人**（性別を問わず2人、1人、または0人）。子どもは親のスキルを一部受け継ぐ。
- 老化・寿命の仕組みはない。市民の区別は子どもと大人のみ（→ 8章）。

## 4.3 住居と通勤

- **住宅**: レベル1つにつきベッド1つ（レベル5で5人）。いくつでも建てられる。
- **酒場**: ベッド4つ（改築しても増えない）。コロニーに1つだけ。
- 住居の割り当ては、町役場の設定で自動（空いているベッドにランダム）か手動かを選ぶ。**市民が自分で住む場所を選ぶ仕組みはない**。
- **通勤距離**: 職場から**100ブロック以上**離れた家に住むと「職場から遠すぎる」と不満を言う。
- **ホームレス**: 家のない市民は夜に町役場に集まる。【ソース確認】7日で不平、14日で要求に変わる。
- **移動**: 特定の道ブロック（pathblocks）の上では速く歩く。研究 Rails でレールを使えるようになる。
- 【実験で確認】**ビルダーの作業半径**は小屋から100ブロック。範囲外の建物は建てられないので、建物の配置はビルダーの小屋の位置に縛られる。

## 4.4 食事と満腹度

- 満腹度は働くと減り、寝るときにも減る。**レベルの高い労働者ほど夜の減り方が大きい**。
- 満腹度が0になると、仕事をやめ、チャットで食べ物を求め続ける。
- MineColonies の料理は**ランク1〜3**に分かれる。バニラの食べ物も食べられるが、幸福度が下がる。
- 【ソース確認】住居レベル3以上では、栄養値が「住居レベル+1」以上の食べ物しか食べない。
- 食料消費量の倍率: 設定 `foodmodifier`（初期値 1.0）【ソース確認】。
- 【実験で確認】パン（栄養値5）は、住居レベル5の市民は食べない（上の栄養値の条件のとおり）。なお、研究の記録では「住居レベル5の市民には6種類以上の多様性が必要だった」とされていて、ソースの読み（「住居レベル」種類以上）と食い違う【要検証】。
- 【実験で確認】**食堂ができると、市民は食堂のメニューに登録された食べ物しか食べない**。登録しないと全員が食べなくなる。
- 【実験で確認】座席のない食堂（Colonial スタイルの cookery1 には座席のタグがない）では、衛兵が食べ物を待ったまま動かなくなる。

## 4.5 幸福度【ソース確認】

各市民の幸福度（0〜10）は、**10個の要因の加重平均**で計算されます（`CitizenHappinessHandler.java`）。

```
幸福度 = min( 10,  10 × ( Σ 係数_i × 重み_i ) / ( Σ 重み_i ) × (1 + 研究ボーナス) )
```

- 係数は **1.0 が中立**、1.0 未満はマイナス、1.0 より大きいとプラス。
- **係数がちょうど 1.0 の要因は、分子・分母の両方から除外される**。つまり、中立でない要因だけで平均をとる。
- 研究ボーナスは市民ツリーの研究（Circus〜Theater）で +5%〜+50%。

| 要因 | 重み | 係数の決まり方 |
| --- | --- | --- |
| 安全（Security） | 4.0 | `(衛兵数+1) / ((衛兵以外の人数+1) × 2/3)`、上限2。衛兵：その他 = 2：3 で 1.0 |
| 食事（Food） | 3.0 | 直近10食の**多様性**（種類数 ÷ 住居レベル）と**質**（MineColonies の料理の数 ÷ max(1, 住居レベル−2)）の平均。それぞれ上限5 |
| 住居（Homelessness） | 3.0 | 住居なし 0、住居あり `住居レベル / 3`。係数1未満が7日続くと ×0.75、14日で ×0.5 |
| 社会（Social） | 2.0 | `(総人口 − 無職 − ホームレス − 病人 − 空腹者) / 総人口` |
| 雇用（Unemployment） | 2.0 | 無職 0.5、職場レベル4以上 2.0、それ以外 1.0。無職が7日続くと ×0.75、14日で ×0.5 |
| 健康（Health） | 2.0 | 病気 0.5、健康 1.0。病気が7日続くと ×0.5、14日で ×0.1 |
| 睡眠（Slept tonight） | 1.5 | 眠れた日 1.0、2日眠れないと 0.8、3日以上で 0.5（衛兵は 1.0） |
| 学校（School） | 1.0 | 子ども: 通学 2.0、通学なし 0。大人は 1.0 |
| 神秘の祭壇（Mystical Site） | 1.0 | `max(1, 祭壇の最高レベル / 2)`（最大 2.5） |
| 職場で暇（Idle at job） | 1.0 | やることがない 0.5、それ以外 1.0。7日続くと ×0.5、14日で ×0.1 |

- 公式 Wiki の説明では、コロニー全体の幸福度が高いと新しく来る市民の初期スキルが高くなり、個人の幸福度が高いと図書館で到達できる Intelligence の上限が上がる。
- 衛兵以外の市民が死ぬと、ほかの市民はその後3日間幸福度が下がる。市民を一人も失わずに襲撃を乗り切ると、コロニー全体にボーナスがある。

## 4.6 病気・死亡【ソース確認】

（`CitizenDiseaseHandler.java` と病気データの確認結果）

| 項目 | 仕様 |
| --- | --- |
| 自然発症 | 一定間隔の判定ごとに小さな確率で発症する。確率は設定 `diseasemodifier`（初期値5。1 = 非常に多い、100 = 非常にまれ）、職業ごとの係数、**食事の多様性**（多様性5で 0.5倍、2以下で 1.25倍）で変わる |
| 接触感染 | 病気の市民とぶつかると **1%** の確率でうつる。研究 Masks で半分を防ぐ |
| 発症しない条件 | 医師は病気にならない。人口が初期市民数以下のあいだは病気にならない |
| 病気の種類 | 病気データの `rarity` を重みとして選ばれる（インフルエンザ 100、麻疹 10、天然痘 1）。1.20 以降はデータパックで変更できる |
| 治療 | 病院のベッドで、病気ごとのアイテムを使って治療する。病院のベッド数 = レベル。病気の市民は仕事をやめて病院へ行く（`EntityAISickTask.java`） |
| 免疫 | 病院で治ると 108,000 tick（現実の約90分、ゲーム内の約4.5日）。研究 Vaccines で10倍。ベッド以外で治ると半分 |
| けが | 体力が6未満の（衛兵以外の）市民は、満腹度が足りていれば医師のところへ行く |
| 喪 | 亡くなった市民の家族（パートナー・親子・兄弟姉妹）と同居人が翌朝から喪に服し、その日は働かない。衛兵と墓守は喪に服さない |
| 蘇生 | 墓守が蘇生を試みる。確率は研究・墓守の Mana・墓地のレベルなどで上がり、最大 12.5% |

- 【実験で確認】衛兵以外の市民は、病気の状態が食事より優先されるので、**病気の間は食事をとれない**。研究室のコロニーでは、これに配給の失敗と病人の密集が重なり、33人中23人が病気になる悪循環が起きた。病院を建て、治療アイテムを確実に届けることで回復した。

## 4.7 襲撃【ソース確認】

（`RaidManager.java` の確認結果）

- **発生条件**: 平和難易度でない、設定 `enablecolonyraids` が有効、そのコロニーで襲撃が許可されている、**オーナー／オフィサーなど権限を持つプレイヤーがログインしている**。
- **襲撃レベル**が **75以上**になると襲撃が起こるようになる。

```
襲撃レベル = { Σ_大人の市民 (5 + スキル合計/100)
             + Σ_建物 (5 + レベル² / 5)
             + 完了した研究の数 × 3 } × min(1, 現在の人口 / 人口上限)
```

- **難易度（1〜14、初期値7）は結果で自動調整される**。失った市民が人口上限の15%を超えると難易度が下がり、次の襲撃までの日数が延びる。5%未満だと難易度が1上がる。
- 間隔: 平均 `averagenumberofnightsbetweenraids`（初期値14夜）、最低 `minimumnumberofnightsbetweenraids`（初期値10夜）。1回の最大人数 `maxRaiders`（初期値80）。

## 4.8 領土

- 創設時は町役場のチャンクの周り**半径4チャンク**（設定 `initialColonySize`）。上限は**半径20チャンク**（設定 `maxColonySize`）。
- 建物を建てると、その建物のチャンクを中心に領土が加わる。解体すると失われる。
- ほかのコロニーとは 8チャンク以上離す必要がある（設定 `minColonyDistance`）【ソース確認】。
- 【実験で確認】建物の設置面積にかかるチャンクが1つでも領土でないと、その建物のワークオーダーはログを残さずに捨てられる。

| 建物 | L1 | L2 | L3 | L4 | L5 |
| --- | --- | --- | --- | --- | --- |
| 町役場 | 1 | 1 | 2 | 3 | 5 |
| 衛兵塔 | 2 | 3 | 3 | 4 | 5 |
| 兵舎 | 2 | 2 | 2 | 2 | 2 |
| その他の建物 | 1 | 1 | 1 | 2 | 2 |

（単位: 追加で確保するチャンクの半径）

# 6. MineColonies においてプレイヤーが介入する要素

MineColonies では、市民が日々の仕事を自分で進める一方で、**「どこに・何を・いつ」作るかの判断の多くはプレイヤー（市長）が行います**。シミュレーションを無人で回すには、これらの判断を自動化するか、固定する必要があります（→ 9章）。

右端の列は、研究室の実装（11章）でその介入がどこまで自動化されているかを表します。「記載なし」は、リポジトリの報告から扱いが読み取れなかったものです。

| 分類 | プレイヤーの介入 | 内容 | 介入しないとどうなるか | 研究での現状 |
| --- | --- | --- | --- | --- |
| 創設 | コロニーの創設 | 補給キャンプ／補給船を置き、町役場の位置を決める | コロニーが始まらない。町役場の位置は後から変えられない | 自動化済み（`/found`）。町役場の位置はオペレーターが目視で選ぶ |
| 配置・建設 | **建物の配置** | ビルドツールで、建物の種類・スタイル・位置・向きを決める | 新しい建物が建たない | 一部自動化。種類は LLM 市長、位置はルール（`placeNext`）。11.4 を参照 |
| 配置・建設 | 建築・改築・修理・移設・解体の指示 | ハットブロックの GUI から指示し、町役場でワークオーダーの優先順位を決める | 建物のレベルが上がらない | 自動化済み（`/requestBuild`、`/rebalanceWorkOrders`、`/removeBuilding`）。改築も LLM 市長が選ぶ |
| 配置・建設 | 道・装飾・整地 | 装飾のスケマティックやシェイプツールでビルダーに頼む。プレイヤーが直接ブロックを置くこともできる | 道がないと移動が遅い（4.3） | 記載なし |
| 配置・建設 | 畑などの作業場所 | 農家の畑（フィールドブロック）、農園の畑などを置く。木こりの伐採範囲を指定する | 生産が始まらない、または範囲が既定のまま【要検証】 | 畑の種の指定は自動化済み（`/setFieldSeed`）。【実験で確認】種を指定しないと農家は働かない |
| 人の割り当て | 雇用 | ハットごとに市民を雇う。町役場で自動雇用に切り替えられる | 自動雇用なら不要 | 自動化済み。スキルに合う職業への配属と入れ替え（`/autoAssignJobs`） |
| 人の割り当て | 住居 | ベッドに市民を割り当てる。町役場で自動に切り替えられる | 自動なら不要（空きベッドにランダム） | 自動化済み。職場に近い住居への引っ越し（`/optimizeHomes`） |
| 生産 | レシピを教える | 職人にレシピを教える（一部は最初から覚えている） | その品物を作れず、リクエストが解決しない | 自動化済み（`/teachRecipe`、教えるレシピの優先順を `crafter_recipes.json` で管理） |
| 生産 | 食堂のメニュー | 食堂で配る料理を登録する | 【実験で確認】食堂ができると、市民はメニューに登録された食べ物しか食べない | 自動化済み（`/setMenu`、`/stockRestaurant`） |
| 生産 | 最低在庫・優先度の設定 | 建物ごとに常に置いておく物、回収の優先度を決める | 既定の動作のまま | 一部（堆肥職人の対象リストを `/setItemList` で登録） |
| 生産 | 初期の動物を連れてくる | 畜産の小屋に最初の2頭（羽）を連れてくる | 畜産が始まらない | 手動（コマンドで動物を呼び出した） |
| 物流 | 手動リクエストへの対応 | 誰も解決できないリクエスト（赤い歯車）にアイテムを渡す | その作業が止まる。設定 `creativeresolve` で自動解決もできる（デバッグ用） | 自動化済み（`supply_bot.js`）。生産が立ち上がった品目は供給を止める |
| 研究 | 研究の選択と材料の用意 | 大学で研究を選び、材料をプレイヤーの持ち物から出す。排他の研究はどちらかを選ぶ | 研究が進まず、多くの建物が解放されない | 自動化済み（`/autoResearch`。浅い順に投入し、材料は消費しない） |
| 人口 | 訪問者の勧誘 | 酒場の訪問者に要求されたアイテムを渡す | 訪問者による人口増加がない（空きベッドと出生では増える） | 未着手（市民の追加は `/spawnCitizen` でできる） |
| 防衛 | 衛兵の任務・召集 | 巡回・警備・追従を設定し、襲撃時に召集の旗で集める | 既定の巡回のまま | 窓口はある（`/guardOrder` で応戦・待機・帰還）。常時の運用は記載なし |
| 防衛 | 防壁・ゲートの建設 | 襲撃に備えた壁やゲートを作る | 襲撃者が入りやすい | 記載なし |
| 外交 | コロニー接続・同盟 | 看板の道でゲートハウスをつなぎ、同盟・敵対を設定する | コロニーどうしが関係を持たない | 未着手（目標①で扱う予定） |
| 出来事 | クエストへの対応 | 受ける・断る・後回しにするを選び、目標を達成する | クエストの報酬・出来事が起こらない | 記載なし |
| 設定 | 町役場の各種設定 | 新しい市民の出現のオン／オフ、権限など | 初期設定のまま | 記載なし |

> 【実験で確認】プログラムからハットを置いたとき、MineColonies は既存の建物との重なりを確かめず、既存の建物を壊してしまう。研究の bridge は、置く前に重なりを確かめている。

# 7. 改造・拡張の手段

MineColonies にない要素を足したり、プレイヤーの介入を自動化したりするための手段です。上ほど手軽で、下ほど自由度が高くなります。研究室ではすでに「外部エージェント」と「VoyagerBridge」の組み合わせで動いています（11章）。これらを層として整理した考え方は 8.1 にまとめています。

| 手段 | できること | 例 | 手間 | 注意 |
| --- | --- | --- | --- | --- |
| 設定ファイル | 用意された数値・オン／オフを変える | 人口上限、病気の起こりやすさ、襲撃の間隔 | 小 | 用意された項目しか変えられない。ファイルの場所は Forge 1.20.1 ではワールドフォルダの `serverconfig/minecolonies-server.toml` と思われる【要検証】 |
| コマンド | 状態の確認、出来事を起こす、市民を増減させる | `/mc colony raid`（襲撃）、`/mc citizens kill`（死亡）、`/mc citizens spawnNew`（市民の追加） | 小 | 多くは OP 権限が必要。公式 Wiki では「デバッグ用」とされている。研究ではサーバーのコンソールに送って使える |
| データパック | データとして定義されている内容を変える・足す | 独自の研究ツリー（政策の選択肢）、病気、クエスト（出来事）、勧誘アイテム、職人のレシピ、市民の名前 | 小〜中 | 仕組みそのもの（計算式や行動）は変えられない |
| スタイルパック（スケマティック） | 建物の見た目・大きさ・独自のハットを作る | 実験用の標準の町並み | 中 | 全レベルで同じ大きさ・同じハットブロックの位置にするなどのルールがある |
| 外部エージェント（外部プログラム） | Minecraft の外のプログラムで判断・計算し、bridge やコマンドでゲームを読み書きする | 研究の council.js・supply_bot.js・social_*.js。税・選挙・人口動態の計算もここに置ける | 小〜中 | 読み書きできるのは bridge とコマンドで用意された範囲だけ（8.1） |
| VoyagerBridge（研究で作った Forge mod）に窓口を足す | MineColonies の Java API を呼ぶ HTTP の窓口を増やす | 統計の項目を返す窓口、倉庫の品目ごとの在庫を返す窓口、市民の転出の窓口 | 中（AI を使った開発で下がる） | すでに導入・運用しているので、導入の手間は増えない。MineColonies 1.20.1-1.1.1231 向けに作られている |
| MineColonies 本体の改変 | 研究で使うバージョンを固定し、本体のソースを直接書き換える | 幸福度の要因を足す、年齢を持たせる、出生の条件を変える | 中〜大（AI を使った開発で下がる） | 本家の更新を取り込むときに差分の管理が必要。GPL-3.0 なので、改変版を配布するときはソースも公開する |

> 新しく別の MOD を導入すると、導入の手間がかかり、バージョンごとに作り直しが必要になります。そのため、窓口が足りないときは**既存の VoyagerBridge に足す**、市民の内部の仕組みそのものを変えるときだけ**本体を改変する**、という方針で考えます。

### 外部ツールとの連携

- AI による集落生成コンペ **GDMC** で使われる **GDMC HTTP Interface**（Minecraft に HTTP でブロックの読み書きを指示する MOD）は、Minecraft 1.19.2・1.20.2・1.21.4・1.21.10〜1.21.11 に対応している。MineColonies（1.20.1 / 1.21.1）と**同じバージョンがない**（2026-09-25 時点）。
- ただし研究室の VoyagerBridge は、すでに HTTP でゲームの状態の取得や建物の配置ができる。地形の高さを返す窓口（`/surfaceY`、`/heightmap`）もある。GDMC の手法を使うなら、GDMC HTTP Interface を持ち込むよりも、**必要な窓口を VoyagerBridge に足す**ほうが手間が少ないと考えられる【要検証】。

## 8.3 経済

### 貨幣・市場・価格

- **現状**: 通貨はない。市民の要求（リクエスト）を、倉庫・配達員・職人が満たす。値段のない**計画経済に近い仕組み**（3.3）。
- **研究での現状**: 未着手。いまは、解決できない要求を `supply_bot` がチート供給で埋めている。
- **現実の仕組み・モデル**
  - 市場での価格決定: 需要が供給を上回れば値上がりし、下回れば値下がりする。決め方にはオークションやダブルオークション（売り手と買い手の注文を突き合わせる）などがある。
  - Sugarscape（Epstein & Axtell, 1996）: 2種類の資源を持つエージェントどうしが交換する人工社会で、交換比率（価格）と富の分布が生まれることを示した、社会シミュレーションの代表例。
- **MineColonies でつなげられる仕組み**
  - リクエストシステムは「誰が・何を・どれだけ必要としているか」という**需要の記録**をすでに持っている。倉庫の在庫は**供給**に当たる。
  - 職人の生産量（`items_crafted` などの統計）は、労働の量の目安になる。
- **実装の層**
  - 価格の計算は A層。建物・市民ごとの需要は C層の `/openRequests` で読める。品目ごとの在庫とコロニー全体の需要は、C層に窓口を足す。
  - 市民が「お金を払って食事をする」など行動まで変えるなら、配給を C層の `/giveToCitizen`・`/transferCitizenItem` で代行するか、D層で食事の行動を変える。
- **設計上の論点**: チート供給を「外からの輸入」とみなすか、なくすか。価格を入れるなら、チート供給にも価格を付けないと市場が成り立たない。
- **測れる指標**: 物価指数、取引量、品目ごとの需給の差。

### 所得・格差

- **現状**: 貨幣がないので所得はない。ただし、市民の間にはすでに差がある。スキル（上限は住居レベルで決まる、4.1）、住居レベル、職場レベル（幸福度の雇用要因が変わる、4.5）、食事の質。
- **研究での現状**: 未着手。スキル（`/citizenSkills`）と職業（`/status`）は C層ですでに読める。
- **現実の仕組み・モデル**
  - 賃金は職種や技能で差がつく。格差は**ジニ係数**や**相対的貧困率**（OECD の定義では、等価可処分所得の中央値の半分に満たない人の割合）で測る。
  - Sugarscape では、能力や初期条件の小さな差から、富が一部に偏る分布が生まれた。年金や社会保障を足して格差への効果を調べる拡張も公開されている。
- **MineColonies でつなげられる仕組み**
  - 職業・スキル・職場レベルを「賃金の決め方」に使える。
  - 住居レベルを「家賃と住宅の質」とみなせる。住居レベルはスキル上限・食事の要求・幸福度に効くので、**所得の差が生活の差につながる仕組みは、すでに半分できている**。
- **実装の層**
  - 賃金の計算は A層。
  - 所得によって住める家を変えるのは、C層の `/assignHome` がすでにあるので **A層＋既存の C層で実現できる**。食べられる料理を変えるのは、配給の代行（C層）か、D層で食堂の配膳を変える。
- **測れる指標**: ジニ係数、相対的貧困率、所得の五分位ごとの幸福度。

### 税・公共財

- **現状**: 病院・学校・図書館・衛兵塔・食堂など、公共サービスに当たる建物はあるが、プレイヤーが資材を出せば建つ。**財源という考え方がない**。
- **研究での現状**: 未着手。ただし、建設は LLM 市長がメニューから選ぶ形なので、**メニューに出す候補を税収で絞れば、建設を財源で制約できる**（council.js の候補の生成部分を変える）。
- **現実の仕組み・モデル**
  - 日本の所得税は、所得が多いほど税率が上がる**累進課税**で、5%〜45% の7段階になっている。消費税は、買った額に一定の率をかける**比例税**。
  - **公共財**（みんなが同時に使えて、使う人を限れないもの。治安・防災など）は、市場では足りなくなりやすいので、税で用意する。
  - Project Sid（2024、8.4 を参照）は、Minecraft 上で AI エージェントに共同のチェストへ納税させ、税率を変えると納税額がどう変わるかを測った。
- **MineColonies でつなげられる仕組み**: 倉庫の在庫（税として集める資源）、ワークオーダー（建設）、研究の材料。公共サービスの水準は、病院のベッド数や衛兵の人数などとして数えられる。
- **実装の層**
  - 税額の計算と、建設候補の制約は A層。
  - 徴収: 市民の持ち物からの移転は C層の `/transferCitizenItem` などで表せる。倉庫から品目を指定して差し引く窓口は C層に足す。
- **測れる指標**: 税収、人口あたりの公共サービスの量、幸福度との関係。

### コロニー間の取引

- **現状**: コロニー接続や同盟はあるが、取引の機能は確認できていない【要検証】。一方で、独自作物はバイオームで育つ場所が決まっていて、上位の料理には複数のバイオームの材料が必要（4.4）。つまり、**地域ごとの得意・不得意が最初から組み込まれている**。
- **研究での現状**: 未着手。研究の目標①（2コロニー間の戦争）では、資源をめぐる競合が観察の対象になっている。取引は、競合と対になる協力の手段として位置づけられる。
- **現実の仕組み・モデル**: 比較優位（リカード）。各地域が相対的に得意なものを作って交換すると、全体の生産が増える。関税や輸送費は交易を減らす。
- **MineColonies でつなげられる仕組み**: バイオームによる作物の違い、コロニー接続の道（ゲートハウスと看板）、倉庫。
- **実装の層**
  - 取引の条件（交換比率、関税）を決めるのは A層。2人の LLM 市長に交渉させる形も考えられる。
  - 物の移動は、C層にコロニー間で移す窓口を足すか、市民を実際に歩かせて運ばせる（`/moveCitizen` と `/transferCitizenItem` の組み合わせ）。
- **測れる指標**: 交易量、交易の前後での食事の多様性と幸福度。

## 8.4 政治

### 政治・選挙・政策決定

- **現状**: MineColonies では、方針はすべてプレイヤー（市長）が決める。市民の不満は幸福度の要因として数値になっている（4.5）。
- **研究での現状**
  - LLM の**統治者2人（都市計画担当・民政担当）が合議**して、建設などの行動を選んでいる。共有の記憶に発言と行動の結果を残し、相手の提案を反映しない場合は理由を返すルールもある。
  - 市民のペルソナには `politics`（忠誠・野心）の値があり、動的な状態として満足度と実際の忠誠（`actualLoyalty`）も持っている。
  - ただし、**市民が統治者を選んだり、政策に投票したりする仕組みはない**。
- **現実の仕組み・モデル**
  - 代表を選ぶ**間接民主制**と、住民投票のような**直接民主制**がある。
  - 選挙制度: 1区から1人を選ぶ小選挙区制や、得票に比例して議席を配る比例代表制（日本はドント方式）など。同じ票でも、集計の方法（多数決、ボルダ方式など）で結果が変わる。
  - 政策は、限られた予算をどこに配るかという形で表れる。
  - **Project Sid**（Altera.AL, 2024, arXiv:2411.00114）: Minecraft 上で、AI エージェント（構成員25人、ほかの人の意見に影響を与える役のエージェント3人、選挙管理者1人）が、税率を定めた「憲法」に意見を出し、改正案に投票した。初期税率は20%で、改正で税率が下がると納税額も下がることを測り、「集団で決めたルールがエージェントの行動を変える」ことを示した。
- **MineColonies と研究の実装でつなげられる仕組み**
  - **有権者の選好**: 幸福度（C層で合計値は読める）、ペルソナの忠誠・野心、動的な満足度。要因ごとの幸福度（どこに不満があるか）は C層に窓口を足せば使える。
  - **候補者**: いまの統治者ペルソナを「候補者」とし、市民の投票で誰が統治するかを決める形にできる。
  - **政策の選択肢**: 建設の優先順位（council のメニュー）、研究（排他の研究は二者択一の政策に当たる。B層で独自の政策ツリーも作れる）、税率、設定値。
- **実装の層**: 投票と集計、統治者の交代は A層（council.js の拡張）で完結しやすい。政策の実行は既存の C層（`/startResearch`、`/requestBuild` など）と B層。
- **測れる指標**: 投票率、政策の支持率、統治者の交代の頻度、政策の前後での幸福度の変化。

## 8.5 人口

### 老化・寿命

- **現状**: 年齢はなく、子どもか大人かの区別（`CitizenData.java` の `isChild`）だけ【ソース確認】。死ぬのは襲撃・モブ・コマンドによる場合だけ。出生はある（4.2）。
- **研究での現状**: 未着手。ただし、ペルソナは出生時に両親から遺伝し、世代（generation）を持っている。死亡は「`/status` に3回続けて現れなかったら死亡とみなす」規則で検知していて、一時的に見えなくなっただけの市民を死亡と誤判定した問題があった（自動で復活させるよう修正済み）。
- **現実の仕組み・モデル**
  - **生命表**: 年齢ごとの死亡率をまとめた表。令和6年（2024年）簡易生命表では、平均寿命は男 81.09年、女 87.13年。
  - **年齢別出生率**（合計特殊出生率）、人口ピラミッド。
  - 定年と**年金**: 日本の公的年金は、現役世代の保険料で高齢者の年金をまかなう**賦課方式**が基本。
- **MineColonies でつなげられる仕組み**
  - 死亡は、既存の「死亡 → 家族と同居人の喪 → 幸福度の低下 → 墓地」の流れにそのままつながる。
  - 老化によるスキルの低下や、引退（働かない大人）は、既存のスキル・雇用の仕組みに乗せられる。引退は C層の `/assignWorker`（解雇）で表せる。
  - 出生は、`ReproductionManager.java` の判定に年齢の条件を足す形になる。
- **実装の層**
  - 年齢の管理と、生命表に従った死亡の判定は A層（ペルソナの台帳に年齢を足せる）。死亡させるのはコンソールからの `/mc citizens kill`。
  - 年齢による能力の変化と出生の年齢条件は D層。
  - ゲーム内の何日を1年とみなすか（時間の縮尺）を決める必要がある。ゲームの速さの倍率が自動で変わることも考えに入れる。
- **測れる指標**: 平均寿命、高齢化率、従属人口指数（働く世代1人あたりの子ども・高齢者の数）、人口ピラミッド。

### 人口の流出・移住

- **現状**: 市民がコロニーを去る仕組みは確認できていない【要検証】。入ってくるのは、空きベッドに来る新しい市民と、酒場の訪問者（勧誘しないと去る。統計 `visitors_absconded`）。
- **研究での現状**: 未着手。目標①で2つのコロニーができると、コロニー間の移住が意味を持つ。
- **現実の仕組み・モデル**
  - Lee（1966）の移動理論: 出身地の**押し出し要因**、行き先の**引きつけ要因**、その間の障害（距離・費用）、個人の事情で移動が決まる。
  - **重力モデル**: 人口が多く、距離が近い地域どうしほど、人の移動が多い。
- **MineColonies と研究の実装でつなげられる仕組み**
  - 押し出し要因 = 幸福度・空腹・病気・無職・ホームレス（C層で読める）、ペルソナの忠誠と動的な満足度。
  - 引きつけ要因 = ほかのコロニーの状態。
  - コロニー接続（ゲートハウスと看板の道）を「移動の経路」として使える。
- **実装の層**
  - 転出するかどうかの判定は A層。
  - 転出そのものを `kill` で代用すると「死亡」として扱われ、喪や統計 `death` が発生してしまう。転出（別のコロニーへの移籍、または消滅）の窓口を C層に足す必要がある。MineColonies の公開されたメソッドで移籍できるかは【要検証】で、できなければ D層。
- **測れる指標**: 転入・転出の数、純移動率、転出した市民の幸福度の内訳。

## 8.6 生活

### 住む場所・職業の選択

- **現状**: 住居と職場は、プレイヤーが割り当てるか、町役場の自動割り当て（空いているベッドにランダム）で決まる。職場から100ブロック以上離れた家に住むと不満が出る（4.3）。
- **研究での現状**: **ルールによる自動割り当ては実装済み**。スキルの適合度（主スキル×2 + 副スキル）で職業を割り当て・入れ替える `/autoAssignJobs`、職場に近い住居へ引っ越させる `/optimizeHomes`、住居を住宅の少ない地区に建てる配置ルールがある。ただし、**市民が自分の好みで選ぶ仕組みではない**。ペルソナには好きな職業・嫌いな職業（`jobPreference`）があり、転職時に満足度が変わる規則はある。
- **現実の仕組み・モデル**
  - 住宅市場: 家賃・住宅の質・通勤の負担を比べて住む場所を選ぶ。都市の中心ほど地代が高くなる仕組みを説明した Alonso の付け値地代理論（1964）がある。
  - 職業の選択とマッチング: 求職者と求人をどう組み合わせるか（例: 安定マッチングを求める Gale–Shapley のアルゴリズム）。
  - **Schelling の分居モデル**（1971）: 近所の住民構成への小さな好みが積み重なって、大きな住み分けが生まれることを示した、社会シミュレーションの古典。
- **MineColonies でつなげられる仕組み**: 住居レベル、通勤距離、家族の同居、職業ごとの主スキル・副スキル（適性）、ペルソナの職業の好み。
- **実装の層**: 選択の計算は A層、反映は既存の C層（`/assignHome`、`/assignWorker`）で**できる**。D層は不要。建物の配置（9章）と組み合わせると、「どこに家を建てるか」と「誰がどこに住むか」を一緒に扱える。
- **測れる指標**: 平均通勤距離、住み分けの度合い（分居指数）、主スキルと職業の一致率、職業の好みとの一致率。

### 市民どうしの関係

- **現状**: 家族関係（パートナー・親子・兄弟姉妹）を持ち、喪は家族と同居人に及ぶ。幸福度の「社会」要因はコロニー全体の割合で、個人どうしの関係ではない。
- **研究での現状**: **研究の中心として実装済み**（11.3）。
  - 家族・同居・同僚・近所（48ブロック以内）の関係ネットワークを、ゲームのデータから作る。
  - 相手ごとに、向きのある信頼・好意・恩義・感謝・恨みを持ち、時間で減衰する（半減期はゲーム内 24,000 tick = 1日）。
  - 困っている市民を見つけて援助するかを判断し、実際に歩いて食料を渡し、結果を関係に戻す閉ループをライブで確認した。
  - 食料1食の配分実験で、関係を入れると親しい相手を選ぶ率が 0.31 → 0.42 に変わった。
  - 課題: 新しいワールドでは関係を復元できる観測が足りない。係数は未較正。
- **現実の仕組み・モデル**: 社会ネットワーク（友人・近所・職場のつながり）、社会関係資本（Putnam。人のつながりが地域の協力や健康を支えるという考え方）、うわさや情報の広がり。
- **MineColonies でつなげられる仕組み**: 同居人・同じ職場・近所、病気の接触感染（ぶつかると1%）。
- **残っている拡張**: 関係を MineColonies の幸福度に反映するには、幸福度の要因を足す D層の改変が必要（要因は `ModHappinessFactorTypeInitializer.java` で登録されている【ソース確認】）。
- **測れる指標**: ネットワークの密度、クラスタ係数、孤立した市民の割合、援助の成功率。

## 8.7 安全

### 犯罪・治安

- **現状**: コロニーの内部での犯罪はない（傭兵が盗みを働く程度）。安全は、衛兵と市民の人数の比率で決まる（幸福度の安全要因、4.5）。
- **研究での現状**: 未着手。ただし、援助の閉ループで作った「市民を相手のところまで歩かせ（`/moveCitizen`）、持ち物を移す（`/transferCitizenItem`）」操作は、向きを逆にすれば**盗み**を表せる。ペルソナには強欲（`greed`）や従順（`obedience`）の値もある。
- **現実の仕組み・モデル**: Becker（1968）の犯罪の経済モデルでは、犯罪で得られる利益と、「捕まる確率 × 罰の重さ」を比べて犯罪を選ぶと考える。抑止には、取り締まり（確率）と罰（重さ）の両方が効く。
- **MineColonies と研究の実装でつなげられる仕組み**
  - 動機 = 困窮（空腹・無職・ホームレス）とペルソナの強欲。
  - 抑止 = 衛兵の人数と巡回範囲、近くにいる市民（関係のネットワーク）。
  - 被害 = 持ち物の盗難。被害者の信頼・恨みの変化は、既存の関係の仕組みに乗せられる。
- **実装の層**: 発生の判定は A層、盗みの実行は既存の C層。衛兵が犯人を捕まえる行動は、C層の `/guardOrder` の拡張か D層。
- **測れる指標**: 犯罪の発生率、検挙率、困窮している市民の割合との関係、被害者の関係の変化。

### 自然災害・環境問題

- **現状**: 外からの脅威は襲撃とモブだけ。ただし襲撃は「突然来て、建物を壊し、結果で次の難易度が変わる」ので、災害の性質（突発・被害・復旧）を一部持っている。
- **研究での現状**: 襲撃などの**警報が関係のネットワークを通って広がるモデル**（Phase 4）を実装済み。現在は観測のみで、市民の移動や戦闘の命令は出していない。脅威と襲撃の状態は C層の `/threats` で読める。
- **現実の仕組み・モデル**: 地震・洪水・火災。事前の備え（防災）と、事後の**復旧**（建物の修理、避難所、医療）。被害を分かち合う災害保険。
- **MineColonies でつなげられる仕組み**: 建物の損傷と修理のワークオーダー、病院（けが人）、避難（襲撃時に家へ逃げる行動）、喪。
- **実装の層**: 災害の発生と規模は A層で決める。被害は、バニラのコマンドでブロックを壊す（`/fill` など）か、襲撃で代用できる。警報の伝播モデルを、実際の避難行動（`/moveCitizen`）につなげるのは既存の C層でできる。コマンドで壊した建物をビルダーが修理するかは【要検証】。
- **測れる指標**: 被害（死者・壊れた建物）、警報の到達率と避難の速さ、復旧にかかった日数。

# 10. 実験環境と注意点

## 10.1 研究で使っている環境

研究室の実装は、次の環境で動いています（2026-10-15 からの運用方針。前期の環境は11章）。

| 項目 | 内容 |
| --- | --- |
| Minecraft / MOD ローダー | 1.20.1 / Forge 47.x |
| MineColonies | 1.20.1-1.1.1231 |
| 前提 MOD | Structurize 1.20.1-1.0.816、Domum Ornamentum 1.20.1-1.0.296 |
| 研究で作った MOD | VoyagerBridge（HTTP API、port 8089）。JDK 17 でビルドする |
| 実験マシン | panama（2026-10-15 に mine-server から移設） |
| LLM | 2026年度は使わない。コロニーは `supply_bot` だけで動かす（前期はローカルの Ollama `gemma4:e4b` で LLM 市長を動かしていた。11章） |
| ワールド | 通常ワールド（起伏あり）。以前はスーパーフラットだったが、鉱山が働けない・チート供給に頼りきりになる、などの歪みがあったため移行した |
| ゲームの速さ | 負荷に応じて倍率を自動で変える（適応ガバナー）。前期は10倍速に固定していた |
| スタイル | Colonial |

- サーバーの MOD は今の版のまま固定し、接続するクライアントをサーバーに合わせる。
- 3人で同じ環境をそろえる場合は、このバージョンの組み合わせが基準になる。VoyagerBridge は MineColonies 1.1.1231 向けに作られていて、ほかのバージョンでの動作は確かめていない。

## 10.2 無人で長時間回すときの注意

- 【ソース確認】オーナーまたはオフィサーがコロニー内のチャンクを読み込むと、設定 `forceloadcolony`（初期値 true）でコロニーのチャンクが読み込まれたまま維持される。プレイヤーが離れたあとも読み込みが続く時間は設定 `loadtime`（初期値20分）で決まり、オーナー／オフィサーが誰もログインしていないと3倍の速さで減る。
- 【実験で確認】**プレイヤーがいないと、コロニーが休眠する**。ワークオーダーの割り当て・日付の進行・リクエストの処理が止まるが、市民は歩き回るので気づきにくい。研究では、VoyagerBridge がコロニーの状態を常に ACTIVE に保つ処理（`keepColoniesActive`）で解決した。
- 【実験で確認】ビルダーの作業半径は小屋から100ブロックで、**建設地のチャンクが読み込まれていないと、ビルダーは何も言わずに待ち続ける**。研究では、建設中の場所のチャンクを自動で読み込む処理（`keepBuildSitesLoaded`）で解決した。
- 【実験で確認】Minecraft の forceload には256チャンクの上限がある。研究のコロニーでは、全建物を覆う範囲が255チャンクに達したことがある。
- 【ソース確認】襲撃は、オーナーやオフィサーなど権限を持つプレイヤーがログインしていることが発生条件の一つ。研究の VoyagerBridge は FakePlayer（`VoyagerAI`）をオーナーとしてコロニーを作るので、無人のときに襲撃が起こるかは【要検証】。

## 10.3 そのほかの注意

- **乱数**: 病気の発症、襲撃の発生、出生などに乱数がある。同じ条件で**複数回試行する**必要がある。研究の社会実験 runner は、乱数の種と結果のハッシュを保存して再現できるようにしている。
- **時間**: Minecraft の1日は現実の20分（倍率 N 倍なら 20/N 分。10倍速なら2分）。研究は現実の時間で進む。【実験で確認】`doDaylightCycle` を false にすると日付が進まず、農家の畑の作業ローテーションなど、日付で動く処理が止まる。
- **高速化の副作用**: 【実験で確認】10倍速などの高い倍率では、プレイヤーがキックされる（浮遊判定やログインのタイムアウトが速く進む）。研究の bridge は、該当するカウンタを毎 tick リセットして防いでいる。
- **倍率と時間の比較**: 倍率が変わると、同じ実時間でもゲーム内の経過時間が変わる。研究では、基本は自動で変わる倍率のまま運転し、時間を測る段階では、倍率を固定するか、記録したゲームの tick 数と倍率から固定の倍率での時間に換算する方針をとっている。
- **外部介入の区別**: チート供給や bridge の操作は、MineColonies 本来の AI の動きとは別物。研究では、結果ごとに「MineColonies 本来の AI・bridge の操作・社会シミュレーションのどれが動かしたか」を記録する方針をとっている。
- **実験用のワールド**: 研究では、ライブの比較試験はメインのワールドではなく、複製したワールドや復元できる状態の保存（snapshot）で行う方針をとっている。
- **初期状態の再現**: スタイルパックで同じ町並みを用意する、`/mc backup` や `/mc colony export` で状態を保存・配布する、などの方法がある【要検証】。
- **情報の新しさ**: 公式 Wiki には古い記述やバージョンによる違いがある。重要な仕組みは、使うバージョンのソースやゲーム内で確かめる。

# 11. 現在の研究の進捗（2026年度前期）

この章は、研究室のリポジトリ [YacobiHime/minecolon_sim](https://github.com/YacobiHime/minecolon_sim) の内容（README・週次進捗報告・引き継ぎ記録・ソース。最終コミット 2026-09-25、最新の週次報告は 2026-08-31）をもとにまとめています。数値や状態は、特に断りがない限りそれぞれの報告の時点のものです。前期の記録として残しているので、10倍速での運転や LLM 市長の稼働などは、今の運用（10.1）とは異なります。

## 11.1 研究の概要

- **何をしているか**: Minecraft（Forge 1.20.1）＋ MineColonies の上で、**LLM が「市長」としてコロニーを自律運営する**社会シミュレーション。プレイヤーの代わりに LLM が建物の種類・職業の割り当て・生産計画を判断し、市民 NPC は MineColonies 本来の AI で生活する。
- **研究の最終目標**（2026-07-03 に確定）
  1. **2コロニー間の戦争**: 独立した2人の LLM 市長が、資源や領土をめぐって衝突するまでを観察する
  2. **狭小空間での効率的発展**: 領土を狭く制限して、市長の優先順位付けや配置の工夫を観察する
  3. **市民の SNS 発言**: 市民の内部状態を言語化し、OASIS などの SNS シミュレーションへ流す
- **いまのフェーズ**: 目標②③の前段として、通常ワールド（起伏あり）で自給自足のコロニーを安定して動かす基盤づくりと、市民どうしの関係・感情・援助を扱う社会シミュレーション層の実装・比較実験。

## 11.2 システム構成

```
┌─ 外部エージェント層（Node.js。サーバーの外で常駐） ──────────────────┐
│ council.js          LLM 市長。統治者ペルソナ2人の合議で行動を選ぶ    │
│ supply_bot.js       不足資材の自動供給（生産が立ち上がると供給を減らす）│
│ persona_daemon.js ほか social_*.js   市民のペルソナ・関係・援助行動    │
│ experiment_runner.js  食料配分などの再現可能な社会実験                │
│ verify_suite.js / work_stats.js / colony_watch.sh  監査・計測・死活監視 │
└──────────────┬───────────────────────────────────────────┘
               │ HTTP（port 8089）
┌──────────────┴─ VoyagerBridge（研究で作った Forge mod） ─────────────┐
│ MineColonies の Java API を直接呼ぶ HTTP API（52 のエンドポイント）     │
│ 無人運転のための常駐処理（コロニーの休眠防止、建設地の読み込みなど）     │
└──────────────┬───────────────────────────────────────────┘
               │ Java API
┌──────────────┴─ MineColonies + Structurize + Domum Ornamentum ──────┐
│ Minecraft Forge 1.20.1 サーバー（MineColonies 1.20.1-1.1.1231）        │
└──────────────────────────────────────────────────────────┘
```

- **VoyagerBridge**: Mixin は使っておらず、MineColonies の公開されたクラスとメソッドを直接呼ぶ。内部のフィールドが必要な箇所（tick の高速化、コロニーの状態機械など）だけリフレクションを使っている。
- **LLM 市長（council.js）**: ローカルの Ollama（`gemma4:e4b`）を使う。統治者2人（Aldric: 都市計画担当、Mira: 民政担当）が日本語で発言し合い、**プログラムが作った「いま実行できる行動」の番号付きメニューから1つを選ぶ**。座標や ID を LLM に書かせないので、存在しない座標や建物を作り出す誤りが構造的に起きない。発言はゲーム内のチャットに表示される。
- 市民の発言（`citizen_voice`）も council から生成している。

## 11.4 建物の配置の現状

- **何を建てるか**: LLM 市長がメニューから選ぶ。メニューには、建物ごとの「アップグレードで何が伸びるか」の知識（`building_knowledge.json`）や、研究で解禁されるかどうかが表示される。
- **どこに建てるか**: VoyagerBridge の `placeNext` が**ルールで決める**（LLM は位置を決めていない）。
  - 中心からの距離と方角で、中央・一次産業・二次産業・学術・軍事の5つの地区に分け、建物の種類ごとに地区を決めている（住居は住宅の少ない地区へ）。
  - 地区の中で、建物の設置面積が既存の建物と重ならず、地表の段差が閾値以下（平坦さゲート）で、ビルダーの小屋から90ブロック以内の、中心に近い位置を探す。
  - 設計図ごとの地面の高さのずれ（`groundlevel` タグ）を補正する。
- **分かった課題**
  - LLM が番号の小さい選択肢を選びやすい偏りがあり、候補がアルファベット順だったため錬金術師の研究所を88回建てた。候補の順番をシャッフルして対策した。
  - 合法な行動だけを出しても戦略として正しいとは限らない。重複設置を332回選び、建物が 78 → 192 棟に膨らんだことがある。
  - 位置は「中心に近く、平らで、重ならない場所」というルールで決まっているため、**都市としてのよい配置（通勤・物流・防衛・景観など）を目的にした最適化は、まだ行っていない**。

- エンドポイントを呼ばなくても動く常駐処理もある: コロニーの状態を ACTIVE に保つ、建設地のチャンクを読み込む、奈落に落ちた市民を戻す、ゲームの速さの自動調整、高速運転中のキック防止。
- Mixin は使っていない。tick の高速化、コロニーの状態機械、ビルダーが持つワークオーダーの ID など、一部の内部のフィールドだけをリフレクションで扱っている。
