## 制約のしくみの全体像（先にまとめ）

この生成器の制約は、次の5層に整理できる。

| 層 | 何を決めるか | 主な制約 |
| --- | --- | --- |
| ① 地形の制約 | どこが建てられる土地か | 高さ、傾き、水、木、既存の建物の特徴マップ |
| ② 配置のハード制約 | 候補地を絞る | 壁の内側だけ／外側だけ、水の上だけ、道からの最大距離、傾きの上限、同じ種類との距離、数の上限、他の構造物と重ならない |
| ③ 配置のソフト制約 | 候補の中から選ぶ | 評価関数（傾き・同じ種類との距離の重みづけ、エージェントごとの独自の評価関数） |
| ④ 時間の制約 | いつ、どのくらいの頻度で置くか | 開始ステップ、実行の間隔、同じエージェントの数、優先度（「きわめて重要」なら他を取り壊せる） |
| ⑤ 用途の制約 | 区画を住宅・工業・商業のどれにするか | 架空の経済（雇用・商品・お金）の条件と、近隣の用途による評価 |

## 章ごとの内容

### I はじめに（Introduction）
- Minecraft を研究の環境として紹介し、地形に適応したそれらしい集落を作る GDMC を説明する。
- 土台は Lechner らのエージェントベースの都市生成。ただしシミュレーション用の環境ではなく、ふつうの（命令型の）プログラムで実装し直した。
- その理由の一つは、5人のチームが並行して開発できるようにするため。建設の過程を、特徴マップと、土地の使い方を決める入札（bidding）のようなしくみでモジュールに分けている。
- 研究の問い: Lechner のエージェントによる町の拡大を Minecraft にうまく移せるか、また共同開発をどう支えるか。

### II 集落生成の関連研究（Related Work in Settlement Generation）
- **Lechner ら**: 住宅・商業・工業の3つの土地利用と、道を作るエージェントを、ゲームのような時刻の刻み（tick）で動かすエージェントベースのシミュレーション（NetLogo を使用）。
- Kelly らの指摘: Lechner の方法は計算コストが高く、生成よりシミュレーションの用途に向く。一方で、いつ止めても結果がある「anytime アルゴリズム」の利点がある。
- Esko と Fritiofsson: 命令型のエージェントによる計画への最初の一歩。ただし、エージェントの組み立て方や衝突の調整の説明は少ない。
- この論文は、**共有の特徴マップと入札のしくみ**で、エージェントどうしの調整を明示的に行う点で、その方向を発展させたと位置づける。
- ほかの GDMC の作品にも触れる。NPC を住人として使うもの、この論文と同じようにモジュール化した効用（utility）に基づく判断をするものがある。

### III 全体の方法（Overall Approach）
4つの段階と、文章の生成からなる。
1. 地形の解析
2. 設計図（ブループリント）の計画
3. 建物の用途の分化
4. ブロックの配置
5. （おまけ）文章による物語

**III.A 地形の解析（Terrain Analysis Phase）**
- 地図の情報を、建設範囲と同じ大きさの2次元の配列（**特徴マップ**）にする。
- 主な特徴マップ:
  - **高さマップ**: 木を取り除いた地面の高さ。木は一時的なものなので、別の「木のマップ」に記録する。
  - **傾きのマップ**: 傾きの急さ。急な所に建てないための制約に使う。
  - **水のマップ**: 水のある場所。
  - **構造物のマップ**: 既存の建物や村の位置（2022年は既存の村がある地図があった）。
- 木の種類などの質的な特徴も集め、ブロックを置くときの材料選びに使う。
- 図2: 既存の村がある300×300の建設範囲から作った、地形の特徴マップの例。

**III.B 設計図の計画（Blueprint Planning Phase）**
- Minecraft にはまだ何も置かず、**メモリの中だけで**町を1ステップずつ育てる。
- **最初の種**: 最も平らな場所に、短い道を1本置いて拡大を始める。
- **1ステップの流れ**: 動いているエージェントが順番に、設計図に何か（道、家、木など）を足そうとする。各エージェントは、成功するか、失敗してその回は何もしない。
- **候補地の選び方（制約の中心）**:
  1. エージェントのハード制約を満たす位置をすべて探す（例: 船は水の上、家は道の近く）。
  2. その中からランダムに一部を選んで評価する。
  3. 評価関数（fitness）が最も高い場所を選ぶ。
- **評価関数の例**: 見張り塔は、高い土地で、かつ他の見張り塔から遠い場所ほど評価が高い。
- **特徴マップの更新（表I）**: エージェントが何かを置くたびに、次のマップが更新され、後のエージェントの判断に使われる。
  - 道のマップ: 道のブロックの位置。重なりを避け、道に接する区画を置くのに使う。
  - 区画のマップ: 計画された区画の範囲。重なりの判定に使う。
  - 城壁のマップ: 城壁のブロック。重なりを避けるのに使う。
  - 壁の内側のマップ: 城壁の内側か外側か（真偽値）。「畑は外側、噴水は内側」のような条件に使う。
- **ステップ数**: 60ステップを標準的な値として使う。性能の実験では30と60を比べている。
- **ランダム性**: 候補の一部をランダムに選ぶことと、エージェントのパラメータによって、毎回違う町になる。
- **取り壊し**: 他のエージェントが作った設計図の要素を取り除けるエージェントもある（例: 教会は場所を確保するために、既存のものを取り壊せる）。
- 図3: 計画の途中の各ステップの設計図。町が育っていく様子。

**III.C 建物の用途の分化（Building Differentiation Phase）**
- 計画の段階では、家の区画は「市民の区画」として用途を決めずに置いておく。この段階で、住宅・商業・工業の3つに分ける。
- 住宅・商業・工業の3つのエージェントが、条件を満たしたときに区画を取り合う。
- **架空の経済**による条件:
  - 住宅のエージェント: 失業率がある値より低いあいだ、人口（労働者）を増やす。
  - 工業のエージェント: 労働者を必要とし、商品と収入を生み出す。
  - 商業のエージェント: 労働者、商品、お金のすべてを必要とする。
- 条件を満たしたエージェントは、**周りの区画の用途**を考えた評価関数で区画を選ぶ。商業は住宅や商業の近くを好み、工業からは離れたがる。
- その結果、似た用途が自然に集まる。経済の条件によって、用途の割合もつりあう。
- 具体的なしきい値や割合の数値は書かれていない（未確認）。

**III.D ブロックの配置（Block Placement Phase）**
- 区画ごとに、建物の種類（教会、家、畑など）専用の生成器で、実際に Minecraft にブロックを置く。
- 地形への合わせ方は建物の種類によって違う。土台を斜面に合わせたり、地形に沿って高さを変えたりする。
- 手続き的な生成の度合いも、色（材料）を入れ替えるだけのものから、完全にランダムな建物までさまざま。このモジュール化で、5人が並行して開発できた。
- 地形の解析で集めた木の種類などで材料を選び、周りのバイオームとなじませる。
- 図4: 平原での集落、上からの眺め、水辺の町、交差点。

**III.E 文章による物語（Written-form Narrative）**
- オランダ語の名前をもとにしたマルコフ連鎖で、町・通り・人の名前を作る。
- 町長の年代記として、市民の建物を建った順に、住所・建築年・住人（名前、年齢、性別、婚姻、子ども）とともに記す。住人には「ネズミの被害」「物資不足」のようなランダムな困りごとがある。船があれば船長の日誌も作る。
- 設計図が1ステップずつ育つので、その順序を「町の歴史」として使える。
- 【メモ】ユーザーの関心（配置のアルゴリズム）からは外れる部分。

### IV 設計図を計画するエージェント（Blueprint Planning Agents）

**表II: エージェントのパラメータ（制約の部品）**

| パラメータ | 内容 | 種類 |
| --- | --- | --- |
| Activation step（開始ステップ） | 何ステップ目から動き出すか（初期値0） | 時間 |
| Activation interval（実行の間隔） | 何ステップごとに動くか（初期値1＝毎ステップ、2なら1つおき） | 時間 |
| Inside-wall-only / Outside-wall-only | 城壁の内側だけ／外側だけに置く | ハード |
| Maximum plots（最大数） | その種類の構造物を置ける数の上限 | ハード |
| Max distance from roads（道からの最大距離） | 道からどれだけ離れてよいか | ハード |
| Water-only（水の上だけ） | 水の上にだけ置く | ハード |
| Critically important（きわめて重要） | 置くために他の構造物を取り壊せる | 優先度 |
| Distance to own kind（同じ種類との距離） | 同じ種類の構造物との最小・最大の距離。重みをつけて評価関数にも使える | ハード／ソフト |
| Slope（傾き） | 許される傾きの上限。重みをつけて評価関数にも使える | ハード／ソフト |
| Custom evaluation function（独自の評価関数） | 設計者がエージェントごとに定義する評価関数 | ソフト |

- 同じ種類のエージェントを複数入れると、その種類の配置の試行回数が増える（例: 市民の区画のエージェントが3つ）。
- エージェントは計画の途中で追加・削除もできる。

**使ったエージェントの一覧**（合計で約40）

| エージェント | 数 | 主な制約・特徴 |
| --- | --- | --- |
| 道 | 3 | 既存の道を分岐させる、経路探索で新しい道を引く、**水の上に橋をかける**（3つの役割の分け方は取得した文章からの読み取りで、要確認） |
| 道の延長 | 道1本につき1 | それぞれの道を伸ばす |
| 城壁 | 1 | 一度だけ動く。それまでの区画をすべて囲む |
| 市民の区画 | 3 | 用途を決めない区画（あとで住宅・商業・工業に分ける） |
| 畑 | 5 | 作物の種類ごと。等高線に沿って広がる |
| 木 | 9 | 城壁ができたあとに動き出す（緑を増やす） |
| 水上の区画 | 3 | **水の上だけ**。大小の船と釣りの足場 |
| 装飾 | 11 | 手押し車、ベンチなど小さな構造物 |
| 見張り塔 | 1 | 高い土地で、他の見張り塔から遠いほど評価が高い |
| 教会 | 1 | 「きわめて重要」。他を取り壊して場所を確保できる |

- 傾きの上限や距離の具体的な値は、本文には書かれていない。

### V 構造物（Structures）

**V.A セル構造（Cell Structures）**
- 同じ大きさの既製の部品（プレハブ）を、正方形のセルとして並べて建物を作る。
- 建物の形は「高さマップ」で表し、隣のセルとの関係で使う部品を選ぶ。例: 教会では、周りより高いセルが塔になる。
- 高さマップをランダムに変えて、構造を保ったまま形に変化をつける。長方形でない形も作れる。
- 図5: 教会を作る部品の一覧。

**V.B 城壁（City Wall）**
- 手順: ①すべての区画を囲む**凸包**（全体を包む最小の凸多角形）を求める → ②その頂点を外側に押し出す → ③頂点どうしを**重みつき A\* 探索**で結ぶ → ④できた線の帯を広げる。
- 地形に沿った有機的な形の城壁になる。
- ブロックを置くとき、壁の上面を **Savitzky-Golay フィルタ**（データをなめらかにする手法）で平らにして、歩けるようにする。一定の間隔で塔を置く。

**V.C 畑（Farms）**
- 割り当てた長方形の区画の中に、最初の小さな畑の「かたまり」を置く。
- **形態学的な膨張**（モルフォロジーの dilation、図形を少しずつ太らせる処理）で畑を広げる。その際、**高さごとに**、同じ高さで、かつ他の構造物に予約されていない所にだけ広げる。
- そのため、畑は**等高線に沿って**広がる（地形の制約がそのまま形になる）。
- 隣り合う畑は、広げたあとに合わさって不規則な大きな畑になる。境界の柵は最後に置く。

### VIII 審査員の感想（User Study (Jury)）
- 8人の審査員の感想をまとめている。
- よい点: 建物の変化、人が住んでいる感じ、全体のまとまり。「城壁が地形の等高線にうまく沿っている」という評価。
- 悪い点: **地形への適応が不十分**（宙に浮いた土台）、年代記が長すぎる、内装の選び方が変、材料が環境になじんでいない。

### IX 今後の課題（Future Work）
- **地形に応じたエージェントの組み合わせ**: 山ではトンネルや鉱山を掘るエージェントを入れるなど、バイオームによってエージェントの一覧を変える。
- 町の大きさに応じて特定の建物を動かす条件（例: 町がある大きさになったら畑を作る、またはその逆）。
- 計画のどの時期に建ったかで建築様式を変え、歴史のある中心市街地を表す。
- バイオームごとの文化のテーマ（砂漠ならエジプト風、タイガならヴァイキング風）。計画の論理にも反映する（例: **川のそばにだけ畑を作る**＝ナイル川流域の文明をまねる）。
- 建物どうしをつなぐ段階（共有の壁、渡り廊下、物干しロープ）。
- 3次元の設計図（張り出した構造物を作れるように）。
- **集落の定量的な分析**（町の大きさ、建物の密度、建物の多様さ、生成できる範囲）は手つかず。ただし今は審査員の主観的な評価のほうが役に立つとする。

### X 結論（Conclusion）
- 成功の主な理由は、モジュール化されたエージェントベースの構造で、開発者が自由に工夫できたことだと述べる。
- エージェントを足したり入れ替えたりすれば、別の設定にも簡単に移せる。

## まとめの項目

- 背景・解こうとしている問題: Lechner らのエージェントベースの都市生成は計算が重い。それを、Minecraft で地形に適応した集落を作るのに使えるよう、共同開発しやすい形に作り直す。
- 手法: 地形の特徴マップ → 約40のエージェントによる60ステップの反復的な計画（ハード制約で絞り、評価関数で選ぶ）→ 架空の経済による用途の分化 → 建物ごとの生成器でブロックを配置。
- 実験・評価の方法: 実行時間の測定（建設範囲の大きさ、ステップ数、バイオーム）と、GDMC の審査員の点数・感想。
- 主な結果: 256×256・60ステップで約2分強。審査員からは全体のまとまりが評価されたが、地形への適応（宙に浮いた土台）には課題が残った。
- 限界・著者が認めている課題: エージェントの一覧が地図によらず同じ。集落の定量的な分析がない。建物どうしのつながり、3次元の計画、内装が今後の課題。

## 追跡する観点

- **水・地形への適応**:
  - 水のマップを作り、道のエージェントが**水の上に橋をかける**。「水の上だけ」の制約を持つエージェントが船や釣りの足場を置く。図4に「水辺の町」がある。
  - 畑は高さごとの膨張で等高線に沿い、城壁は地形に沿う。一方で、宙に浮いた土台という批判もある。
  - 「川のそばにだけ畑を作る」は今後の課題（川を活かした配置はまだない）。
- **評価の数値化と客観性**:
  - 著者も、集落の定量的な分析（大きさ、密度、多様さ）を今後の課題に挙げている。ただし、今は審査員の評価のほうが役に立つという立場。
  - 評価関数は配置を選ぶためのもので、できあがった集落の評価には使っていない。
- **集落の種類・性格（都市か田舎か、密か疎か）**:
  - 城壁の内側（噴水など）と外側（畑など）を区別する制約で、「中心の市街地と周辺の農地」という構造ができる。
  - 架空の経済で、住宅・商業・工業がそれぞれ集まる。用途地域に近い構造が自然にできる。
  - ただし、どの地図でも同じエージェントの一覧を使うので、作られるのは常に「城壁のある中世風の町」。地図に合わせて集落の種類を変えることは、今後の課題（地形に応じたエージェントの組み合わせ）。

## MineColonies の研究に使える点

- **制約のしくみをそのまま流用できる**【推測】: MineColonies の建物の種類ごとに「エージェント」を作り、表IIのパラメータで制約を書ける。
  - 例: 衛兵塔（Guard Tower）は「同じ種類との距離」と「高い土地」、農家の小屋は「城壁の外側だけ」「傾きの上限」、漁師の小屋は「水のそば」、住宅は「道からの最大距離」。
- **特徴マップ**（高さ、傾き、水、既存の構造物）は、MineColonies のコロニーの地形を解析するときの基本の形として使える。
- **用途の分化の「架空の経済」を、MineColonies の本物の経済に置き換えられる**【推測】: この論文では雇用・商品・お金は配置を決めるための架空の数値だが、MineColonies では市民の仕事、資源、食料が実際に動く。配置の結果を、実際の経済の動きで確かめられる。
- **段階的な成長**: 1ステップずつ町を育てる方式は、MineColonies でコロニーが段階的に大きくなる過程（研究で人口の上限が上がるなど）と対応づけやすい。
- **評価関数に暮らしの指標を足せる**: 今の評価関数は、傾き、距離、高さなど地形と見た目のためのもの。ここに「職場と家の距離」「食堂・倉庫への距離」を足すのが、卒研との差分になりうる。

## 疑問・気になった点

- 傾きの上限、道からの最大距離、同じ種類との距離などの**具体的な値**が書かれていない。コード（公開されていれば）で確認したい。
- 道のエージェントが「どの場所まで水を渡るか」（川の幅の上限など）の判断方法。
- 架空の経済の数値（失業率のしきい値、商品やお金の増え方）と、住宅・商業・工業の最終的な割合。
- 「入札（bidding）」のしくみが、本文で具体的にどう実装されているか（候補を出し合って比べるのか、単に順番に置くのか）。
- 特徴マップの解像度（1ブロック＝1マスか）。

## 方針セッションへの申し送り

- **「ハード制約で候補を絞り、評価関数で選ぶ」エージェントの反復的な計画**は、MineColonies のハットの配置を AI で決める場合の、最も直接的な土台になる。パラメータ（表II）が制約の部品として整理されているので、MineColonies 用の制約にそのまま置き換えやすい。
- この論文の住宅・商業・工業の分け方は、**架空の経済**に基づく。MineColonies を使えば、「配置の計画（この論文の方式）→ 実際の市民の暮らし（MineColonies）→ 通勤距離や不満の数で評価」という流れが組める。架空の経済を本物のシミュレーションで検証する、という位置づけにできる。
- 城壁の内側・外側の区別は、**中心市街地と周辺**の構造を作る制約として使える。コンパクトシティ（内側に集める）と分散型（外側にも広げる）を、制約の設定を変えて比べる実験の形が考えられる【推測】。
- 著者自身が、集落の**定量的な分析**（大きさ、密度、多様さ）を今後の課題としている。暮らしの指標で定量的に評価することは、このギャップを埋める方向になる。
