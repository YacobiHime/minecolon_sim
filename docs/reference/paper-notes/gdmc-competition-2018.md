- 書誌: Christoph Salge, Michael Cerny Green, Rodrigo Canaan, Julian Togelius／2018（arXiv v1: 2018-03-27、v2: 2018-07-31）／Foundations of Digital Games (FDG) 2018 の Procedural Content Generation ワークショップ（arXiv の Comments 欄で確認。10ページ、図5枚）／https://arxiv.org/abs/1803.09853
- 読んだもの: arXiv の要旨ページと PDF（2026-09-30）。PDF の本文はツール経由で取得したため、細かな言い回しは原文で再確認するのが望ましい。

## 章ごとの内容

### 1 はじめに（INTRODUCTION）

**1.1 概要（Overview）**
- 論文全体の案内。コンペの課題、技術的な枠組み（どう提出するか）、評価基準を説明すると述べる。
- ただし重点は技術的な細部ではなく、「このコンペがどんな研究課題を提示し、なぜそれが科学的に意味があるか」に置くと宣言している。
- 鍵となる概念として「適応的な生成（adaptive）」と「全体的な生成（holistic PCG）」の2つを予告する。

**1.2 動機（Motivation）**
- AI研究ではコンペが進歩を促してきたとして、DARPA のチャレンジや RoboCup を例に挙げる。
- Minecraft は「勝ち負け」がない自由なゲームなので、AIの課題を自分たちで定義する必要がある。集落生成はその一つの形。
- 既存の PCG（手続き的コンテンツ生成）コンペも、自動指標ではなく人間の審査員で評価しているので、このコンペもそれに倣う。
- Minecraft には標準の村の生成機能があるので課題は「解ける」ことがわかっている。一方で、人が作った集落のほうが明らかに優れているので、改善の余地がある。
- 図1〜4で標準の村の問題点を見せている。
  - 図1: 自動生成の畑・家に、プレイヤーが建物を足した集落（人の手で良くなった例）。
  - 図2: 同じ型の建物の繰り返し、地形を無視して段差や谷で途切れる道。
  - 図3: 斜面に置かれた建物で、扉が地面から数ブロック上にあり、村人が入れない。
  - 図4: 同じ建物ばかり、水の中の石造建築、不自然な高架の道。

**1.3 目的（Aims）**
- **内容への適応（adaptivity to content）**: 3次元の地図のような、豊かで多次元の入力に意味のある形で反応すること。地図には「ここは川沿い」「ここは急斜面」のような、読み取って解釈しないとわからない性質も含まれる。
- **全体的な PCG（holistic PCG）**: 生成された別々の種類のコンテンツや観点どうしが、互いにかみ合うようにすること。原文では "different types of generated content ... fit with each other" に近い言い方。
- これを実現する方法の例として、階層的な生成、反復的な修正、要素どうしが作用し合うシミュレーションに基づく生成を挙げている。

### 2 人間並みの集落生成に向けた課題（CHALLENGES FOR HUMAN-LEVEL SETTLEMENT GENERATION）

**2.1 環境と地形への適応（Adaptation to Environment and Terrain）**
- 現実の集落は、その土地の材料、気候に合った建築、地形の利点の活用、不利な点を補う構造物などを通して環境を反映している。
- 集落は地形を選んで作り変える（運河、トンネルなど）が、大きな地形の特徴は尊重する。
- 既存のAIによる生成は、地面を平らにして固定のテンプレートを置くものが多い。
- よい作品は、地図ごとに異なる集落を作り、地形と地元の材料に合わせ、地形の改変は最小限にするべきだとする。

**2.2 身体性の視点からの機能性（Functionality from an Embodied Perspective）**
- Minecraft の集落に必要な機能として、移動のしやすさ（歩ける、扉、橋）、敵モブからの防御（照明、壁、防御の構造物）、資源の提供（食料、クラフト）を挙げる。
- 機能はプレイヤーだけでなく、NPC の村人にとっても必要。村人はプレイヤーと似た必要を持つという前提。
- 「物語上の機能」もある。例えば傾斜屋根は、Minecraft では雨や雪の対策として必要ないが、現実の慣習をまねることで説得力が出る。
- 生成器は、プレイヤーのアバターの大きさや、身体を持ってできる行動を考えて、「できること（アフォーダンス）」を増やすべきだとする。

**2.3 それらしく、想像をかき立てる物語（Believable and Evocative Narrative）**
- 人が作った集落は、文化的な特徴や歴史の物語を反映している。
- よい集落は、地形やバイオームに合った物語を感じさせる。
- シミュレーション的な手法なら、集落の発展の段階を見せ、作られたものに「実際の発展の歴史」という裏づけを与えられる。
- 物語上の機能は、ゲーム上の機能を補える。例えば木材に頼る集落なら、製材所や運搬の設備があると、ゲーム上の機能は増えなくても物語が強まる。

**2.4 見た目の美しさ（Visual Aesthetics）**
- 現実の建築は美的な原則に基づいて設計されるが、美しさを自動で判定するのは難しい。
- 既存の Minecraft の MOD は、あらかじめ作ったテンプレートに頼るので、変化や地形への適応が限られる。
- 集落全体の美しさは、建物の並び、見通し（sight lines）、見た目の統一感で決まる。
- 美しさは他の観点を補強するべきで、例えば要塞の見た目は、防御の機能と、その集落の物語上のアイデンティティの両方を表す。

**2.5 評価基準（Evaluation Criteria）**
- 審査員は、3つの地図それぞれについて4つの観点を0〜10点で採点し、その合計が得点になる。
- 2.5.1 **適応性（Adaptability）**: 地形に合わせているか、環境の材料を反映しているか、地形の特徴を活かしているか、地図ごとに違う集落になっているか。
- 2.5.2 **機能性（Functionality）**: 敵モブからの防御、プレイヤーの移動のしやすさ、より速い移動手段、道のわかりやすさ、資源への到達、食料、村人への機能、規模の適切さ。
- 2.5.3 **それらしく想像をかき立てる物語（Believable and Evocative Narrative）**: 物語を感じさせるか、各部分の役割がわかるか、環境と整合しているか、物語を支える機能があるか、発展の過程がうかがえるか、文化や歴史をほのめかしているか。
- 2.5.4 **見た目の美しさ（Visual Aesthetics）**: 見た目の魅力、様式の統一感、適度な変化、信じられる見た目か。

### 3 コンペの詳細（COMPETITION DETAILS）

**3.1 枠組み（Framework）**
- 参加者は、オープンソースの Minecraft 地図エディタ **MCEdit** の Python フィルタとしてプログラムを書く。フィルタは、パラメータと、実行される `perform` 関数をまとめたもの。
- 枠組みを選んだ理由は、参加しやすさ、Minecraft との接続の簡単さ、評価の手間の少なさ。
- 開発用のテスト地図が配布される。Java での参加への拡張も検討課題として触れている。
- 【補足】2018年時点の方式で、現在の GDMC は GDMC HTTP Interface や GDPC を使う（gdmc-reading-guide.md 参照）。

**3.2 サンプルのエージェント（Example Agent）**
- 主催者が見本として **CASG（Cellular Automata Settlement Generator）** を提供している。
- 手順: 二分空間分割（binary space partitioning）で土地を庭の区画に分ける → 柵の支柱で境界を作る → ランダムな大きさの長方形の建物を置く（角の高さを変える）→ 柱と天井を作る → セルオートマトンでガラスと石の壁の模様（窓のようなもの）を作る。
- 図5がその出力例。地形への適応はほとんど考えられていない見本【推測：図の説明から判断】。

**3.3 提出（Submission）**
- アルゴリズムのコードと、任意の2ページの説明文（手法や特徴。採点はされない）を提出する。
- コードの公開は推奨されるが必須ではない。
- 計算時間の制限: 256×256の地図で、普通の PC で10分を大きく超えないこと。
- 使えるブロックの数や資源の扱いには、計算時間以外の制限はない。

**3.4 評価（Evaluation）**
- 提出されたアルゴリズムを、参加者が見たことのない**3つの地図**で実行する。
- 結果は匿名化してから審査員に見せる。
- 審査員は地図の中心に出現し、**ピースフルモード**（敵モブが襲ってこない）で見て回るが、サバイバルモードのプレイヤーの立場で考えて採点する。
- すべての審査員がすべての作品を評価する予定。作品が多すぎる場合は、複数の段階に分けて一部の審査員で審査することもある。
- 審査員の人数や顔ぶれ: 「専門家の審査員団」とあるだけで、具体的な人数は書かれていない（未確認ではなく、原文に記載なし）。
- 地図、生成された集落、説明文、（許可があれば）コードを公開する。

### 4 関連研究（RELATED WORK）

**4.1 手続き的コンテンツ生成（Procedural Content Generation）**
- PCG の分類に照らすと、このコンペはオフライン生成、自動実行、そして**プレイヤーではなく環境に適応する**生成に当たる。
- 比較対象として、GVGAI のレベル生成・ルール生成部門、Mario AI Championship を挙げ、いずれも人の審査で評価していると述べる。
- 地図という豊かな多次元の入力に適応する点が、通常のパラメータ調整型の生成と違う。

**4.2 PCG の評価方法（Evaluation Methods for PCG Methods）**
- 評価方法を3種類に分けて紹介する。
  - **直接評価**: 建物の密度や平均距離のような指標を計算する。
  - **シミュレーションによる評価**: AIのキャラクターを動かして、到達できるか、資源に届くかを確かめる。
  - **対話的な評価**: 人がプレイして評価する（このコンペの方式）。
- 参加者が自分で集落を多数生成し、人の評価を使って機械学習モデルを訓練し、それを提出する、という使い方もありうると述べる。
- 例として Tanagra、Ropossum、Sentient Sketchbook を挙げる。

**4.3 都市の生成（City generation）**
- コンピュータグラフィックスの研究として、Kelly と McCabe の Citygen、Parish らの都市生成（現実のデータを組み込む）、Groenewegen らの土地利用に基づく配置の生成を挙げる。
- Minecraft の MOD として **Millénaire** と **Lost Cities** を紹介。Millénaire は文化ごとに異なる村があり、村人が資源を集めて新しい建物を建てる。
- **Ultima Ratio Regum** を階層的な生成の例として挙げる（先に国や文化を作り、それに合った建築や言葉を生成する）。

**4.4 生成としてのシミュレーション（Simulation as Generation）**
- シミュレーションを「評価」に使うのではなく、発展の過程そのものをシミュレーションして「生成」する考え方。
- 例: **Dwarf Fortress** は、何百年分の歴史をシミュレーションして背景の物語を作る。
- 欲求や動機を持つ村人のエージェントが、生き延びるために家を建て、世界を作り変えるシミュレーションなら、実際の発展の過程を反映した意味のある集落ができうる。ただし規模を大きくするのが難しい（計算量）。
- Minecraft 風の世界で、内発的な動機を持つエージェントが環境を変える研究の試作にも触れている。

### 5 今後の展開（THE ROAD AHEAD）
- **共創（co-creativity）**: 人が作った既存の集落を、様式を保ったまま拡張させる課題。様式の転写や、作り手の意図の理解が必要になる。
- Project Malmo を使い、プレイ中にリアルタイムで人と協力して作る支援も考えられる。
- ほかのコンテンツとの統合: 集落の歴史を文章で生成し、ゲーム内の本として置く（町の年代記）。これはのちの **Chronicle 部門**につながる考え。宝探しとその手がかりの物語を作る案もある。

## 補足：AIはどうやって Minecraft とやり取りするか（ユーザーの質問への回答、2026-09-30）

- **2018年の方式（この論文）**: 提出物は MCEdit の Python フィルタ。ゲームを起動せずに、**地図のセーブデータを直接読み書きする**。ブロックもセーブデータに直接書き込む。ゲーム内のキャラクターがブロックを置くわけではない。
  - 論文は、生成はゲーム開始前にすべて終わり、開始後はエージェントが手を加えないと述べている。
  - 論文の「エージェント」は、提出されたプログラムそのものを指す（ゲーム内のアバターではない）。
  - AIはゲーム画面を見ない。ブロックの種類と位置のデータを読んで地形を把握する。地図のどこまで読めるかの細かな規定は、この論文には書かれていない（未確認）。
- **現在の方式**: 多くの参加者が **GDMC HTTP Interface** を使う。起動中の Minecraft に入れる MOD で、外部のプログラムが HTTP でブロックの読み書き、高さマップやバイオームの取得、コマンドの実行、エンティティの操作などを行う。これも**ブロックを直接設定する方式**で、画面の画像は返さない（GitHub の README で確認）。
- **5章の Project Malmo**: 将来の案として、アルゴリズムをゲームの中に置き、プレイ中に人を支援する形が挙げられている。2018年の時点では採用されていない。
- **エージェントを使う作品（AgentCraft、2022年の優勝作など）**: エージェントは、プログラムの中で動くシミュレーション上の存在だと考えられる【推測：AgentCraft の要旨ページからの判断。本文は論文⑤を読むときに確認】。AgentCraft は、HTTP 版の枠組みを使って、建設の様子をリアルタイムに見せている。

## まとめの項目

- 背景・解こうとしている問題: 既存の集落生成（Minecraft 標準の村や MOD）は、地面を平らにしてテンプレートを置くだけで、地形に合わず、要素どうしがかみ合わない。人が作る集落との差を埋めることを課題にしている。
- 手法: 論文自体は新しい手法の提案ではなく、コンペの設計（課題・枠組み・評価基準）の提案。見本として CASG を示す。
- 実験・評価の方法: 実験はない。評価方法として、専門家が3つの未知の地図でプレイヤー目線で歩き回り、4観点を0〜10点で採点して合計する方式を定めている。
- 主な結果: 結果はない（提案論文）。成果は、適応性・機能性・物語・美しさの4観点による多次元の評価の枠組みを定義したこと。
- 限界・著者が認めている課題:
  - 美しさの自動判定は難しいので、人の審査に頼る。
  - 作品が多いときの審査の負担（段階的な審査を想定）。
  - シミュレーションによる生成は、規模を大きくするのが難しい。
  - MCEdit / Python に限る枠組み（Java への拡張は検討中）。

## MineColonies の研究に使える点

- **2.2 の「身体性の視点からの機能性」**は、市民が実際に歩いて働く MineColonies と直接つながる。特に「機能は村人（NPC）にも必要」という前提は、市民の行動で機能性を測る研究の根拠になる。
- **4.2 の「シミュレーションによる評価」**（AIのキャラクターで到達可能性などを確かめる）は、MineColonies の市民の移動を評価に使う発想の先行例として引ける。
- **4.4 の「生成としてのシミュレーション」**で、欲求を持つ村人のエージェントが町を作ることが、すでに2018年の時点で有望な方向として挙げられている。Millénaire（村人が資源を集めて建物を建てる MOD）は MineColonies に近い先行例として比較対象になる【推測：両者の比較は原文にはない】。
- **2.5.2 の機能性の項目**（防御、移動、交通、道のわかりやすさ、資源、食料、村人、規模）は、MineColonies で測れる量（移動距離、食堂への到達時間など）と対応づけやすい。
- **4.3 の Groenewegen らの土地利用に基づく配置**は、用途地域・職住近接を考えるときに追って読む価値がある文献【推測】。

## 疑問・気になった点

- 2018年大会の実際の参加数・審査員数・結果はこの論文にはない。論文②（Salge ほか 2020）で確認する。
- 「規模の適切さ」（2.5.2）が具体的に何を指すか（人口に対する建物数か、地図に対する大きさか）は原文で詳しく書かれていない。
- 採点は4観点の単純合計で、観点どうしの重みづけの議論はない。のちの論文③で、点数化そのものへの批判が出てくる点と合わせて読む。
- 4.3 の Citygen、Parish らの論文は、都市の形（道路網・区画）を扱う古典なので、都市形態学側の文献として押さえる必要があるかもしれない。

## 方針セッションへの申し送り

- GDMC は初年度から「身体性（住む人・村人の立場）」と「シミュレーションとしての生成」を重要課題に掲げている。MineColonies を使う研究は、この2点に正面から取り組む位置づけで説明できそう。
- 評価の3分類（直接評価・シミュレーション評価・人の評価）は、卒研で配置を評価する方法を整理する枠組みとしてそのまま使える。都市の社会課題（通勤時間、サービスへのアクセス）は「直接評価」と「シミュレーション評価」の両方で測れる。
- GDMC の生成は、プログラムがデータを直接読み書きする「上から全体を見て置く」方式で、ゲーム内のキャラクターが歩いて建てるわけではない。MineColonies では、市民（ビルダー）がゲーム内で実際に建設し、住み、通勤する。「配置の計画」は GDMC 型、「その配置での暮らし」は MineColonies の市民、という役割分担が考えられる。
- GDMC の評価観点には「通勤」「職住近接」「サービスへのアクセス」のような都市計画の観点は明示的には含まれていない（機能性の中の移動・資源へのアクセスが最も近い）。ここが差分になりうる。
